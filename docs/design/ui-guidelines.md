# UI 开发注意事项：命名与显示

> 适用于 Agent Memory 的所有图形界面（DSH 侧栏工作台、提案卡、未来的独立客户端）。
> 事实基础：**用户不知道 `mem-20261017-dc3339cf` 这个序列代表什么**。任何界面都不应该要求用户理解内部 ID。

## 1. 一律不展示内部 ID

- `mem-…`、`prop-…`、`session-…` 等内部标识**不得出现在常规界面文案**里（列表、详情、提案卡、错误提示、按钮）。
- 内部 ID 只允许出现在：命令手册/导出文件/日志/开发调试；即使出现，也要配一句「这是给程序看的编号」。
- 用户需要指代一条记忆时，用**库编号**（`F-01` / `P-01` / `E-01`），不是内部 ID。

## 2. 类型只用中文

| 内部值 | 界面文案 |
|---|---|
| `fact` | 事实 |
| `pitfall` | 坑 |
| `exp` | 经验 |
| 提案 `supersede` | 修订 |
| 提案 `delete` | 删除 |

不要出现 `fact`、`supersede`、`delete` 这些英文/内部词；未来新增类型先在服务端做中文映射，再进 UI。

## 3. 已有记忆：库编号 + 内容总结

- 格式：`F-01 中文优先偏好`
- 内容总结 **≤ 12 个字**，由服务端 `summarize()` 统一截断（按字符计，中文按字）。
- 库编号由服务端 `serialsFor()` 按「类型分组、组内时间从晚到早」生成；编号只用于口语指代，**不写进存储、不作为 API 主键**。
- 列表、详情、提案目标、审批卡都用同一份 `display` 字段，客户端不得自己拼 ID 或另算编号。

## 4. 新内容 / 提案内容：只有总结

- 提案要修改成的新内容没有库编号，只显示 ≤12 字总结，例如「新内容：中文优先与图形界面」。
- **提案卡必须提供「查看详情」开关**：展开后显示目标全文、修改后的摘要与正文、理由；不能只有总结而没有展开入口。
- 新记忆（未来若开放）同理：先有总结，批准并落库后才获得库编号。

## 5. 编号规则（V3 会扩展）

- `F` = 事实、`P` = 坑、`E` = 经验；两位补零（`F-01`）。
- 组内排序：`created_at` 从晚到早；同时间按 id 倒序，保证稳定。
- V3 会出正式的「序号命名对照表」；在此之前，编号只是展示序号，不允许被外部系统当作稳定标识引用。

## 6. 实现约定

- 服务端（`packages/dsh/src/gui.ts`）统一产出 `display` 字段：`displayName(serial, abstract)` 与 `summarize(text, 12)`。
- 客户端只渲染 `display`；详情用 `serial + 类型中文 + 维护者 + 日期`，不显示 `id`。
- **列表**：每个分组最多直接展示 8 条，其余放进下方独立滚动区并提示剩余数量；展开详情时详情卡出现在工具条之后、列表之前，并滚回顶部。
- **状态互斥**：打开提案、偏好与规则、执行搜索时，先收起详情与修订草稿，避免两个界面叠在同一页。
- **不展示对话出处**：详情卡不列「用户 #seq」这类 provenance；搜索也不显示「有出处/无出处」。出处数据保留在 API/导出/审计里，UI 不呈现。
- **配色**：使用 Chrome 中性色 + `#1a73e8` 强调（深色 `#8ab4f8`）；所有颜色走 `am-*` 令牌，不写死 hex。
- 新增任何 UI 文案/按钮/错误提示，先过一遍本文件；涉及 ID 的一律改为「库编号 + 总结」或「内容总结」。

## 7. 验收

- 单元测试：`S14.9`（总结 ≤12 字、`display` 以库编号开头、不含 `mem-`）。
- 客户端静态检查：`S13.1`（详情用 `serial`、提案用 `target.display` / `replacement.display`，不再渲染 `detail.data.id`）。
- 人工走查：列表、详情、提案卡、审批后回执四处都看不到长串 ID。
