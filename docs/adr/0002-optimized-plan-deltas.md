# ADR-0002 · 与优化版方案的差异处理

- 状态：已采纳（仅限对 S1 有影响的部分）
- 日期：2026-10-17
- 依据：工作区新增的 `V1.0-开发方案-优化版.md`（2026-10-17）与 `V1.0-开发方案.md`
- 相关：[ADR-0001](0001-skeleton.md)

## 背景

S1 开始后，工作区里出现了一份 `V1.0-开发方案-优化版.md`。两份方案对 S1 的**验收目标一致**——未知配置拒绝、core 不依赖 DSH、包边界检查通过——但有几处取舍不同。本记录说明 S1 采纳了哪些、哪些留到后续阶段，避免"两份文档各说一套"。

## 采纳的调整

### A1 · 不预建空包

优化版 §0.6、§2.2 明确"暂不为未验证的 v1.2 提前建设多后端抽象、空 MCP 包和付费空钩子"。

S1 因此**不建 `packages/mcp`**（原方案 §3.1 的骨架）。如果 MCP 真的成为需求，再按原方案 S8 的形态加回来：只读适配器、约 200 行映射、core 一行不改。代价很小，提早建包的代价是"看起来有接口，其实没人验证"。

同理，S1 没有 `entitlement` / `meter` 钩子；它们的价值取决于是否存在第二个客户端，而不是取决于接口写得多早。

### A2 · 安全边界只按实际权限描述

优化版 §6.3 指出：目录放在工作区之外**不等于** DSH 进程读不到；"防直接文件写入"只在工具沙箱真正拦住这些路径时成立，否则只是工具层策略。

因此 `docs/policy.md`、`packages/core/src/paths.ts` 的注释都改成"在当前 DSH 工具沙箱下不可达，这是工具层边界，不是 OS 级隔离，需 S0 实测"。S1 不把目录命名当安全机制，也不在文档里承诺未验证的隔离。

### A3 · 注入预算只承诺字符数

优化版 §0.5 指出字符数不能稳定换算成 token。S1 的配置项全部以**字符**计量，`docs/config.md` 也只说字符；没有任何"约 1200 token"的说法。改按 token 计量属于 S3（注入）的验收项，届时用锁定版本的实际计量方式，并标明是估算还是实测。

### A4 · 不复制原始会话，也不预建空目录

优化版 §3.3、§6.2 要求证据引用指向 DSH 已有会话日志，不在记忆目录里复制整份轨迹。S1 的目录骨架据此**不创建 `archive/sessions`**（原方案 §4.1 有），也不创建 v1.1 才用的 `strategy/`：`mem init` 只建 `memories/{fact,pitfall,exp}`、`proposals/{pending}`、`.index/`、`.state/` 与数据目录本身。等 S5 做收尾蒸馏时，`provenance` 直接记 `session_id + event_seq + quote_hash`，不搬正文。

### A5 · 元数据格式留到 S2 决定

优化版 §3.2 反对自研"部分 YAML"解析器：要么用成熟解析器并限制 schema 字段，要么改用 JSON 元数据块 + `JSON.parse`。S1 不碰 frontmatter，这条不影响已完成的部分；S2 开工前必须先按这条做一次选择并记 ADR。已经落地的"受限解析、超出即拒绝"原则继续有效——无论选 YAML 还是 JSON，都不允许半解析。

## 留到后续阶段的差异

| 优化版要求 | 现状态 | 落到哪 |
|---|---|---|
| S0 兼容性 Spike（锁定 DSH/Node 精确版本、验证 assemble/压缩/审批/沙箱） | 未做；本 S1 按开发方案 §7 执行 | S2 前的 S0（若采纳优化版，S0 应先于存储层） |
| 预算按 token 计量 | 目前只有字符预算 | S3 |
| 会话快照键含 session ID / memory revision / prompt schema 版本 | 未实现 | S3 |
| `RULES.md` 区分「机器门禁」与「模型指引」 | 未实现 | S5 |
| 召回固定查询集与 Recall@5/Precision@5 门槛 | 未实现 | S3（先建查询集基线） |
| 锁文件 + 精确版本 + 发布包 SHA-256 | 已有 `package-lock.json`；无发布脚本 | S6 |

## 三条仍然成立的原则（两份方案一致）

1. `core` 不依赖宿主；`dsh` 不直接读写文件；所有入口共用一套校验；
2. 启动/配置/策略失败必须响亮，不静默降级；
3. 每条"硬"约束要么有代码检查、要么有测试，否则只能标"软"。

## 后果

- S1 的交付范围比原方案略小（少了空 MCP 包），但两条方案在 S1 的验收项全部满足；
- 若最终采纳优化版，下一步应先做 S0 兼容性 Spike，再进 S2；若沿用原方案，可直接进 S2，但 S0 的结论（DSH 版本能力）仍需在 S3 前补齐；
- 所有后续文档提到"边界"时，必须区分**工具沙箱边界**与**OS 权限边界**。
