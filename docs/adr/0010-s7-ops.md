# ADR-0010 · S7 运维与发布

- 状态：已完成（命令、备份/校验、历史审计、真实 DSH 全流程走查）
- 日期：2026-10-17
- 阶段：S7（计划 3–4 人日；实际 1 个工作日，AI 辅助，含测试）
- 依据：[V1.0-开发方案-v1.3.md](../research/V1.0-开发方案-v1.3.md) §10；[ADR-0009](0009-s6-closeout.md)

## 问题

前六个阶段有数据与协议，但没有人能安全地看、搬、删：没有 export/备份、没有 purge 墓碑、没有一屏 inspect，也没有对 100+ 份历史会话的机器审计。

## 选择

1. **`mem inspect [--limit N] [--json]`**：只读一屏输出——各 kind 活动数、规则清单与类别、最近 N 条 journal、预算占用、隔离的数量与 journal head。
2. **`mem export <dir>` / `mem pack <dir>`**：复制 `memories/`、`proposals/`、`.state/journal/`、`.state/policy.seal.json`、`SOUL/USER/RULES`、`config.toml`、`policy.json`、`.state/distill-rejected.json`；生成排序后的 `SHA256SUMS`；不复制 `.index/`、快照、锁与 txn（派生物）。
3. **`mem purge <id> --accept`**：人 T2；journal 写 `delete` 墓碑（`purged:true` + 原因），删文件，重建 manifest/目录；引用该 id 的待审提案文件作废并记 `audit`；`reload` 不再把“有 delete 但文件缺失”当隔离。
4. **历史审计**：`scripts/audit-sessions.mjs` 只读扫描 `~/.dsh/sessions` 的 v4/v3 日志；v4 缺 `id`/`role` 退出 1，v3 只计数（加载时由 DSH 迁移）；`repair-dsh-session.mjs` 只处理 v4，遇到旧格式明确提示“audit only”，不再报 not found。
5. **恢复步骤**：`docs/ops.md §8` 写清 journal 断链/截断的人工恢复顺序（停写、导出、判断、用备份当数据目录、`doctor`→`rebuild`）。
6. **升级前备份**：发布流程先用 `mem export` 生成带 `SHA256SUMS` 的目录并保留上一版；本阶段提供命令与校验测试，自动触发留在发布脚本（S7 之后）。

## 被否方案

- **purge 直接删文件不写 journal**：重建时无法区分“已清除”和“文件丢失”。
- **export 连 `.index/`/快照一起复制**：派生物会掩盖源数据问题，恢复时应重建。
- **审计改 v3 日志**：v3 的消息身份由迁移层产生，直接改会偏离升级路径。
- **inspect 输出全文**：一屏放不下；`--json` 给机器，`--audit` 全量渲染留 V1.1。

## 证据

- **190 个测试**（1 个 S7.5 手动用例 skip）；`npm run ci` 全绿。
- S7.1 export→新目录 rebuild 活动集合一致；S7.2 purge 文件/manifest/目录项/提案/journ​al 墓碑；S7.3 inspect JSON；S7.4 clean 命令面；S7.6 `SHA256SUMS` 改动检测与恢复。
- `node scripts/audit-sessions.mjs`：**106 个日志（54 v4 + 52 v3），0 缺陷，0 错误**。
- 备份/校验：`mem export` + `verifyExport`；篡改任一文件后校验失败，还原后通过。

## S7.5 走查追加（2026-10-17）

真实桌面全流程走完：新建会话 → 写入（引用 `memory_context` 的 `event_seq`）→ 召回命中 → 提案（supersede）→ `mem decide --batch accept` → `/compact` → 重启应用 → `mem rebuild` + `mem inspect`；重启后 `memory_recall` 返回替代后的 `mem-20261017-16850c76`，旧条目仍可 `memory_read` 追溯。

走查发现并修复三处：

1. **宿主缓存**：`MemoryStore.recall` 与 `MemoryStore.read` 不再依赖进程内旧索引/旧快照，查询前先 `reload()`；否则 CLI 的 `add`/`decide` 已改盘，宿主仍返回旧结果或对刚写入的 id 报“找不到”。代价是每次查询多一次磁盘扫描（数据量在预算内）。
2. **提案证据断链**：`memory_propose` 的 replacement 现在必须带 `evidence`，`service.propose` 在 propose 时绑定 `provenance`（`session_id`/`event_seq`/`speaker`/`quote`/`event_sha256`）；`addMany` 写记录时保留它。原先 `service.propose` 丢弃证据、`addMany` 硬编码 `provenance: []`，proposal accept 后只剩 `author: human` 的空出处记录。格式规则允许 human 记录带 provenance，因此不冲突。
3. **一致收紧**：closeout 的 evidence `quote` 加上 ≤160 字符校验（与 `bindEvidence` 对齐），超限时丢弃该候选而不是在写提案时抛错。

语义取舍：采纳后的记录仍是 `author: human`（人签字负责），证据只证明"当时确实这么说"，不改变责任归属；`provenance_verifiable` 因而是 true（修复前为 false）。

不回溯旧数据：修复前生成的替代记录（如 `mem-20261017-16850c76`）保留空 provenance；不写迁移脚本，历史以 journal `decide` 行为准。

最终签收证据（2026-10-17 重启后实测）：`memory_propose` 返回的提案 JSON 自带 provenance（event_seq 7277、quote「重启好了」、event_sha256）；`mem decide --batch accept` 后，宿主 `memory_read mem-20261017-c3634f09` 返回同一条 provenance，`memory_recall` 命中该记录且 `provenance_verifiable: true`；`mem-20261017-16850c76` 被 `supersedes` 取代但文件仍可读。

## 偏差与回滚

- **S7.5 真实 DSH 全流程已完成**（见上一节）；修复了走查暴露的宿主缓存（recall/read）、提案证据断链与 closeout 证据长度问题，新增 S4.4/S4.6 追踪用例。
- **`inspect --audit` 全量渲染**未做；当前 `inspect` 显示最近 N 条 journal（`--limit`），Q6 记为已解决（最小可用）。
- **T9（home junction 实路径）与 T10（锁 PID 启动时间）顺延 V1.1**：前者需要明确的 `realpath` 策略，后者 Node 无跨进程启动时间 API；当前锁仍保证“超时失败、绝不覆盖”。
- 回滚：删除 `ops/ops.ts`、CLI 的 inspect/export/pack/purge 分支与 `scripts/audit-sessions.mjs`；数据侧 purge 墓碑保留，旧代码把文件缺失当隔离（可用备份恢复）。
