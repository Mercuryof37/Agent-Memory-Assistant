# ADR-0019 · UI 命名：库编号 + 内容总结，永不展示内部 ID

- 状态：已实现（待真实桌面复验）
- 日期：2026-10-18
- 阶段：V2 P2 收尾（UI 命名修订）
- 依据：[UI 开发注意事项](../design/ui-guidelines.md)

## 问题

提案卡与详情仍会露出 `mem-20261017-dc3339cf` 这类内部 ID。用户明确表示不知道它代表什么；ID 对指代、口头沟通和审批都没有帮助。

## 选择

1. **不展示内部 ID**：列表、详情、提案卡、错误提示都不出现 `mem-…` / `prop-…`。
2. **类型全中文**：事实 / 坑 / 经验；提案动作 修订 / 删除。
3. **已有记忆 = 库编号 + 内容总结**：`F-01 中文优先偏好`，总结 ≤12 字。
4. **新内容 = 只有内容总结**：新内容没有库编号，审批后才获得编号。
5. **服务端统一生成 `display`**：新增 `summarize(text, 12)` 与 `displayName(serial, abstract)`；`buildList`、`buildProposals` 返回 `display`，客户端只渲染它，不自行截断或拼 ID。
6. **详情行**改为 `F-01 · 事实 · 人工维护 · 2026-10-17`，不再显示 `detail.data.id`。
7. **命令手册**里的 `/mem read <编号>` 改成 `<库编号>`（如 F-01），并注明「编号一律是库编号，不是长串内部 ID」；提案审批不需要编号，用「提案」面板或 `/mem review`。

## 被否方案

- **短 ID（mem-5e13）**：仍然要求用户理解编码；不如总结直观。
- **只在前端截断摘要**：各页面会截得不一样，且提案卡需要目标编号 + 总结的组合，必须服务端统一产出。
- **编号写进存储/作为 API 主键**：编号会随排序变化，不适合做主键；V3 才有正式命名对照表。

## 证据

- `ci` 全绿：**240 个测试**。新增 `S14.9`：`summarize` ≤12 字、`display` 以库编号开头且不含 `mem-`、无编号的新内容只显示总结；`S13.1` 断言详情用 `serial`、提案用 `target.display` / `replacement.display`。
- 现有提案 `prop-mem-20261018-5e131e65` 的目标现在显示为 `F-01 用户偏好：界面文案与工具描述`（12 字总结）。

## 偏差与回滚

- 库编号仍按当前排序动态生成，刷新后可能变化；V3 命名表落地前，界面不承诺编号永久稳定。
- 导出 JSON/日志仍含内部 ID（程序需要），但不进入常规界面。
- 回滚：恢复详情显示 id、提案卡拼接 serial + 全摘要；删除 `display` 字段与本文档。
