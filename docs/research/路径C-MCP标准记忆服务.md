# 路径 C：MCP 标准记忆服务（跨客户端、与宿主解耦）

> **一句话**：不把记忆做进 DSH 插件，而是单独跑一个"记忆服务"，用 MCP（模型上下文协议）把查询/写入工具暴露出来；DSH、Claude Code、Cursor、Codex 都连同一个服务，记忆从此属于你而不是属于某个 agent。
>
> **适配环境**：任意支持 MCP 的宿主（DSH `0.2.0-rc.2` 具备 MCP 客户端能力）/ 本地或局域网
> **调研基准**：2026-10-17（star 数为当日 GitHub API 实测值）

---

## 一、这条路径用的是什么技术

前两条路把记忆"长"在 DSH 里。这条路把它**搬出去**，变成独立进程。

做法是：起一个服务（本地 stdio 或 HTTP），它自己管存储、自己管检索；对外只说一种话——**MCP**，也就是一段 JSON-RPC：客户端问"有哪些工具"，服务答"我有 `search_nodes`、`create_entities`、`add_observations`…"；客户端调工具，服务返回结果。DSH 通过 MCP 客户端连上它，就像连一个普通的 MCP server。

这么做换来三件事：

1. **解耦**。记忆不再依赖 DSH 的内部接口（`systemPrompt.assemble`、`appendPluginRecord`），DSH 怎么破坏式更新都伤不到它。
2. **共享**。同一个服务可以同时给 DSH、Claude Code、Cursor、Codex 用。换工具不丢记忆。
3. **标准化**。MCP 是公开协议，工具描述自解释，agent 自己就能发现该调什么。

代价也很实在：**多了一个进程**，而且**你对"怎么注入上下文"的控制力变弱**——因为注入这步回到了宿主手里，你只能控制"查到什么"，控制不了"怎么拼进去、会不会击穿缓存"。

这条路有三种典型形态，选哪种决定了你后面所有的麻烦：

| 形态 | 存储 | 代表 | 适合 |
|---|---|---|---|
| **实体-关系图** | 单个 JSONL 文件 | 官方 `server-memory` | 想要"谁和谁有关系"的轻量图推理 |
| **关系型 + 本地嵌入** | SQLite / 自有后端 | `mcp-memory-service`、`agentmemory` | 想要语义检索但不想上云 |
| **图数据库** | Neo4j / FalkorDB | `memento-mcp`、`graphiti` | 需要时序知识图谱（重，见路径 D） |

### 技术栈一览

| 层 | 选型 | 作用 | 是否必须 |
|---|---|---|---|
| 协议 | MCP（JSON-RPC 2.0，stdio 或 HTTP） | 宿主 ↔ 记忆服务的契约 | ✅ 必须 |
| 服务实现 | Node/TS 或 Python | 常驻进程 | ✅ 必须 |
| 存储 | JSONL 图 / SQLite / 自家后端 | 记忆本体 | ✅ 必须 |
| 检索 | 子串匹配 / FTS5 / BM25 / 向量 | 召回 | ✅ 必须 |
| 语义（可选） | 本地 ONNX 嵌入 或 API 嵌入 | 模糊召回 | 可选 |
| 并发 | 锁文件 或 数据库事务 | 防写坏 | ✅ 必须 |
| 宿主接线 | DSH 的 MCP 客户端配置 | 让工具可见 | ✅ 必须 |
| 只读出口 | 只读 MCP server（如 `memento` 的读侧） | 给外部客户端查 | 推荐 |
| 运维 | 日志、健康检查、备份 | 长期跑 | ✅ 必须 |

### 优势

- **不被宿主绑架**：DSH 升级、换工具、甚至不用 DSH 了，记忆还在。
- **多 agent 共享一份记忆**：这是路径 A/B 做不到的。
- **实现可替换**：协议不变，服务可以从官方的换成自研的，宿主侧零改动。
- **有真正的成熟项目**：这条路的头部项目 star 数从 424 到 10 万，踩坑的人多、文档全。
- **可以只读接入**：先用只读 MCP server 试水，不冒写坏数据风险。

### 劣势

- **注入不可控**：你只能决定"召回什么"，决定不了"怎么进提示词、要不要冻结"。前缀缓存优化得靠宿主。
- **多一个进程要养**：启动、崩溃重启、端口、日志、备份，都是新增运维面。
- **官方 server 不是 Markdown**：它是 JSONL 图模型，**会失去"打开文件就能读"这个核心资产**。
- **性能有额外一跳**：每次召回都要过 JSON-RPC，高频调用会感知到延迟。
- **生态质量参差**：官方实现很稳，但带 Neo4j/OpenAI 的那些对一个个人工作台来说太重。

### 技术要求

| 项 | 要求 | 说明 |
|---|---|---|
| 编程能力 | 会用现成 server 即可；自研需懂 MCP + JSON-RPC | **门槛比 A/B 低**——可以零代码起步 |
| 协议理解 | 知道 MCP 工具的 `inputSchema`、资源、stdio/HTTP 传输 | 中等 |
| 机器资源 | 一个常驻进程；向量型要 200–500MB 内存 | 本地 ONNX 嵌入可用 CPU |
| 外部账号 | 图数据库型**需要**（Neo4j + OpenAI key）；ONNX 型**不需要** | 选型时注意 |
| 运维负担 | 中（进程守护 + 备份） | 比路径 A 高，比路径 D 低 |
| 上手时间 | **半小时**（装现成的）到 1 周（自研） | 这是最快的路径 |

## 二、适用与不适用

**适合你，如果**：
- 你不止用 DSH，还想让 Claude Code / Codex / Cursor 共享记忆；
- 你受够了 DSH 破坏式更新（Amadeus 就因这个"大重构"过）；
- 你想先零代码试水，验证"记忆到底有没有用"再投入自研；
- 你能接受"注入方式不完全受控"。

**不适合你，如果**：
- 你要求注入必须是冻结快照、必须字节稳定（这条路给不了）；
- 你坚持记忆必须是"人可读的 Markdown"（官方 server 是 JSONL）；
- 你不想再养一个进程。

## 三、架构与数据模型

```
┌──────────┐   ┌──────────┐   ┌───────────┐
│   DSH    │   │ Claude   │   │  Cursor   │   ← 任意 MCP 客户端
│          │   │  Code    │   │  / Codex  │
└────┬─────┘   └────┬─────┘   └─────┬─────┘
     └──────────────┼───────────────┘
                    │ MCP (JSON-RPC 2.0)
                    ▼
          ┌───────────────────┐
          │  Memory MCP Server│
          │  工具 / 资源 / 通知 │
          └─────────┬─────────┘
                    ▼
          ┌───────────────────┐
          │ 存储（JSONL / SQLite）│
          └───────────────────┘
```

**官方 `server-memory` 的数据模型**（值得理解，因为它就是"知识图谱最小实现"）：

- **实体**（entity）：`name` + `entityType` + `observations[]`
- **关系**（relation）：`from` + `to` + `relationType`
- **观测**（observation）：挂在实体上的一条事实字符串
- 工具 9 个：`create_entities` / `create_relations` / `add_observations` / `delete_entities` / `delete_observations` / `delete_relations` / `read_graph` / `search_nodes` / `open_nodes`
- 资源：`memory://knowledge-graph`（整图 JSON），变更时发 `notifications/resources/updated`

**它的并发方案值得单独抄**（这是路径 A/B 也受益的工程细节）：

> 每次写操作在记忆文件旁取独占锁 `<file>.lock`；持锁期间每 15 秒刷新；崩溃遗留的锁若同机进程已退出立即清理，否则 30 秒无刷新后由等待者（经 `.lock.break` 守卫）打破；**60 秒拿不到锁则工具报错而不是覆盖文件**。该机制依赖本地文件系统的独占创建语义，**网络文件系统不安全**。

## 四、关键实现点

**1. 先用只读方式试水。** 有的项目自带只读 MCP server（如 `dsh-memento` 的 `-mcp` 包），先让外部客户端查，确认数据有价值再接写入。

**2. 想清楚"谁负责注入"。** 这是这条路最容易被忽略的设计问题。MCP 只管存取，注入回到宿主——所以你必须在宿主侧另外做注入策略（比如 DSH 里用一个小插件把召回结果按固定边界拼进去），否则记忆会"存在但没人用"。

**3. 别把图模型当万能。** 官方 server 的 `search_nodes` 只做**字段子串匹配**，没有语义检索、没有"字面替换 + 先读后写 + 版本冲突"语义。想要后者，得选关系型/向量型实现。

**4. 锁与备份要一起设计。** 锁文件只在本地文件系统可靠；备份必须在无写入时做，否则会拿到半写状态。

**5. 暴露工具要克制。** `agentmemory` 有 54 个 MCP 工具——工具一多，模型选择成本就上去了。自己写时，**6–9 个工具**是舒适区。

**6. 安全边界。** MCP 服务常驻且能读写记忆，等于多一个攻击面。至少：只监听回环、要 token、日志脱敏。

## 七、开发流程（照 Amadeus 的做法）

这条路适合"**先验证、后自研**"，所以流程要比 Amadeus 多一个"选型验证"阶段：

```
docs/research/
  01-mcp-server-survey.md      ← 候选对比（工具数、存储、依赖、许可证）
  02-trial-log.md              ← 真实跑 3 个 server，记录：装了多久、召回准不准、进程稳不稳
  03-injection-design.md       ← 宿主侧怎么把召回结果拼进提示词（关键，别漏）
  04-adr-自研or采用.md          ← 决策记录：为什么采用/自研
```

**验证清单**（每个候选都跑一遍）：
1. 装起来要几步？有没有 key？
2. 写入 20 条中文记忆，用 10 个查询测命中率。
3. 杀掉进程再拉起，数据还在吗？
4. 并发写两条，会丢吗？
5. 工具描述模型看得懂吗？实际调用率高不高？

## 八、里程碑与验收

| 阶段 | 产出 | 验收标准 |
|---|---|---|
| M0（半天） | 跑通官方 `server-memory` | DSH 能列出 9 个工具并成功读写一条 |

| M3（1–2 天） | 宿主侧注入 | DSH 里召回结果能进提示词，且**同一会话字节稳定** |
| M4（1 天） | 运维兜底 | 进程守护、日志、备份、只读巡检 |
| M5（可选） | 自研 server | 只在你确认现成方案不够时做 |

## 九、风险、许可证与退出策略

| 风险 | 影响 | 应对 |
|---|---|---|
| 注入没人做 | 记忆"存了但没用" | M3 是必做项，别跳 |
| 官方 server 是 JSONL | 失去人可读性 | 若在意，选关系型实现；或双写 Markdown 权威副本 |
| 进程挂了 | 记忆不可用 | 守护 + 健康检查 + 降级为"本轮无记忆" |
| 许可证 | 根仓库混合文本 | 以 `src/memory` 子目录的 MIT 声明为准；引用时写明 |
| `memento-mcp` 停更 | 无人修 bug | 不选；或只借鉴其版本历史设计 |
| MCP 安全 | 攻击面扩大 | 回环监听 + token + 日志脱敏 |

**退出策略**：把存储导出成 JSON/JSONL，随时可迁回路径 A（文件）或 B（SQLite）。**协议是标准，数据要能带走。**

## 十、结论

**这是"最少代码、最快验证"的一条路，但不该是你的终点。**

它最大的价值是**解耦**：DSH 的破坏式更新伤不到它，换 agent 也不丢记忆。如果你的核心痛点是"我不敢把记忆绑在 DSH 上"，这条路直接命中。

**但它有两个明确的天花板**：注入不可控（前缀缓存优化得自己补），官方实现的检索很弱（子串匹配）。

**推荐用法**：用它做**第一阶段验证**——半天装一个，跑 20 条中文记忆，你就知道"记忆对自己到底有没有用"。如果验证有用，再决定是继续走这条路自研 server，还是回到路径 A/B 把注入与检索做扎实。
