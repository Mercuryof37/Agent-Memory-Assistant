# 路径 D：语义 RAG 记忆（向量检索 + LLM 抽取）

> **一句话**：让模型把对话里的"事实"抽出来，转成向量存进向量库；下次任务开始前，用语义相似度把相关的几条捞回提示词——不靠关键词、不靠文件，靠"意思相近"。
>
> **适配环境**：DeepSeek Harness `0.2.0-rc.2`（已有多家官方 DSH 插件）/ 需本地或云端模型
> **调研基准**：2026-10-17（star 数为当日 GitHub API 实测值）

---

## 一、这条路径用的是什么技术

前三条路都要"人决定记什么"。这条路把这件事交给模型。

完整链路是四步：

1. **抽取**：对话进行中（或结束后），用一个 LLM 把"值得记的事实"抽成结构化条目——"用户偏好 TypeScript 而非 JavaScript"这种；
2. **向量化**：把条目文本送进嵌入模型（embedding），得到一串数字向量；
3. **存储**：向量 + 原文 + 元数据一起落进向量库（LanceDB / pgvector / Qdrant 等）；
4. **召回**：下次提问时，先把问题也向量化，找距离最近的 K 条，再拼进提示词。

真正让它变好用的，是围绕这四步加的三层工程：

- **混合检索**：向量召回 + 关键词（BM25/FTS5）双路，再用 reranker 重排——纯向量对"专有名词、版本号、错误码"往往不灵；
- **后台捕获**：不必等用户说"记住"，在会话结束或压缩前自动抽取（Hermes、MemOS、Hindsight 都这么做）；
- **图关系**（可选）：把实体和关系也存进去，支持"顺着关系走"的召回（Graphiti、OpenViking 是这一档）。

这条路是四条里**召回能力最强**的，也是**运维成本最高**的。

### 技术栈一览

| 层 | 选型 | 作用 | 是否必须 |
|---|---|---|---|
| 抽取模型 | 任意 chat LLM（可路由到便宜模型） | 从对话抽事实 | ✅ 必须 |
| 嵌入模型 | 云端 embedding API 或本地（ONNX / llama.cpp / FastEmbed） | 文本 → 向量 | ✅ 必须 |
| 向量库 | LanceDB / pgvector / Qdrant / 内置索引 | 近邻检索 | ✅ 必须 |
| 关键词索引 | FTS5 / BM25 | 第二路召回 | 强烈推荐 |
| 重排 | reranker（交叉编码器或轻量模型） | 提高精确率 | 推荐 |
| 图存储 | 可选（图库或关系表） | 实体关系召回 | 可选 |
| 捕获触发 | 会话结束 / 压缩前 / 每 N 轮 | 自动写入 | 推荐 |
| 服务形态 | 常驻服务（HTTP/MCP）或库调用 | 对外接口 | ✅ 必须 |
| 宿主接线 | DSH 插件 / MCP 客户端 | 让 DSH 用上 | ✅ 必须 |
| 运维 | 日志、成本看板、备份、模型版本管理 | 长期跑 | ✅ 必须 |

### 优势

- **语义召回最强**：问"上次那个关于缓存击穿的问题"，即使原话里没有"缓存击穿"四个字也能召回。
- **不用人操心记什么**：抽取与写入自动化，对"懒得维护记忆"的人友好。
- **容量近乎无上限**：向量库能装几万到几百万条，不会被 10000 字符卡死。
- **已有官方 DSH 插件**：MemOS、ReMe、EverOS、WeKnora 都提供了 DSH 集成，**不用从零写**。
- **可选的图能力**：需要"实体关系推理"时有路可走。
- **有公开 benchmark**：MemOS 自述在 LoCoMo / LongMemEval 上有分数，可作为横向参考。

### 劣势

- **必须依赖模型**：要么付 API 费，要么在本地跑嵌入模型（占内存、首次加载慢）。
- **多一个常驻服务**：向量库 + 抽取服务 + 宿主，故障点显著增多。
- **成本会失控**：后台捕获 = 持续消耗 token。Hermes 社区的实测抱怨就是"每隔几轮跑一次 self improvement，很费 token"，有人因此弃用。
- **可审计性下降**：记忆是"模型抽出来的"，不是"你说过的原话"，出错时更难定位。
- **许可证有坑**：`OpenViking` 是 **AGPL-3.0**，`WeKnora` 的 API 返回 `NOASSERTION`（README 标 MIT），商用前必须核实。
- **自动化会反噬**：见下面第二节，这是这条路最重要的警告。

### 技术要求

| 项 | 要求 | 说明 |
|---|---|---|
| 编程能力 | 会用现成插件即可；自研要懂 RAG 全链路 | 采用现成方案时门槛低 |
| 机器资源 | 向量库 1–4GB 内存；本地嵌入需 2–8GB | 云端嵌入则只需网络 |
| 外部账号 | **需要**：嵌入/抽取 API key（或本地模型替代） | 这是与路径 A/B 最大的分野 |
| 成本意识 | 必须能估算"每会话多少 token" | 否则月底账单会教育你 |
| 运维负担 | **高**：服务守护 + 备份 + 模型版本 + 成本监控 | 四条路里最高 |
| 上手时间 | 1 天（装现成插件）到数周（自研） | 装插件很快，调好很慢 |

## 二、必须先知道的一个研究结论（会改变你的设计）

这条路最大的诱惑是"自动化"：让它自己总结、自己整合、越用越聪明。但有一篇论文给了**反直觉的硬警告**——知乎那篇《Agent 长期记忆怎么做才安全？先别急着总结》解读的 [《Useful Memories Become Faulty When Continuously Updated by LLMs》](https://arxiv.org/abs/2605.12978)：

> 有用记忆被持续整合后，一开始能帮 Agent，后来反而拖后腿。**GPT-5.4 不用记忆时 100% 做对 19 道题，记忆整合 10 轮后准确率掉到 52.6%。**

论文给出的五条工程结论，几乎逐条否定了"全自动记忆"的默认设计：

1. **原始经历和提炼出的经验要分开管理**——不能揉进一个反复被改写的文件；
2. **整合要过门槛**——不要任务一结束就自动总结；
3. **提炼要慢**——先积累证据，同类经历足够多再提炼；
4. **写进去的经验要能验证**——至少不让 agent 把原本能做对的任务做错；
5. **出错能撤回、不可靠能标记**。

**这意味着**：如果你走路径 D，第一个要砍掉的可能就是"后台自动整合"。Hermes 之所以提供 `write_approval: true` 并让"有损的 LLM 合并整理默认关闭"，大概就是踩过这个坑。

**落到实现上**：
- 自动**捕获**（存原始事实）可以有；
- 自动**整合/改写**（把多条合成一条结论）应当**默认关闭**，或严格门槛 + 可撤回；
- 每条记忆要留 `source`（哪次会话、哪条消息），否则"这条经验从哪来"永远说不清。

## 三、适用与不适用

**适合你，如果**：
- 你的记忆量会很大（几百到几万条），文件与 SQLite 都开始吃力；
- 你确实需要"意思相近就能召回"，关键词检索已经不够；
- 你愿意付 API 费或让本地机器跑模型；
- 你想直接用现成插件，少写代码。

**不适合你，如果**：
- 你的记忆主要是"我的人格 + 我的偏好 + 我们的约定"——那几十条就够，路径 A 更合适；
- 你无法接受"记忆内容由模型抽出来、不是原话"；
- 你没有精力做成本监控；
- 你要严格可审计、可逐条人工编辑。

## 四、架构与数据模型

```
对话流
  → 捕获触发（会话结束 / 压缩前 / N 轮）
  → LLM 抽取候选事实（结构化：content / type / scope / confidence / source）
  → 去重与冲突处理（可与已有条目比对）
  → 嵌入（embedding）→ 写入向量库 + 原文表
  → [下一次任务前]
  → 查询扩展（可选）→ 双路召回（向量 + BM25）→ rerank → 取前 K
  → 拼进提示词（有界）
```

**记忆条目最小字段**（综合 MemOS / Hindsight / 知乎 MVP 结构）：

```json
{
  "id": "mem_001",
  "content": "用户希望技术文档多用真实案例",
  "type": "user_preference",
  "scope": "global | project:<id>",
  "tags": ["writing", "docs"],
  "confidence": 0.95,
  "source": { "session_id": "...", "event_seq": 42 },   // 必填，用于回溯
  "created_at": "2026-10-17",
  "updated_at": "2026-10-17",
  "valid_from": "2026-10-17",
  "invalid_at": null,                                    // 事实失效用「标记」不用删
  "embedding_model": "text-embedding-3-small@v1"         // 换模型要能识别旧向量
}
```

> **`source` 和 `embedding_model` 这两个字段最容易被省掉，但它们是后期救命的。** 前者让你能回答"这条记忆从哪来"，后者让你在换嵌入模型时知道哪些向量要重建。

## 五、关键实现点

**1. 先关掉自动整合。** 见第二节。只做"捕获原话级事实"，不做"自动提炼规律"。

**2. 混合检索，别只用向量。** 版本号、错误码、文件路径这类 token，纯向量几乎必错。向量 + BM25 + rerank 是当前公认的稳妥组合。

**3. 检索要两阶段。** 先拿轻量索引（ID + 摘要，约 50–100 token/条），筛选后再取全文——`claude-mem` 用这个把 token 省了约 10×。

**4. 换嵌入模型要能重建。** 记录每条记忆用的模型版本；换模型时旧向量会与新查询向量不同空间，召回会静默变差。

**5. 去重要在写入前做，且阈值要可调。** 太松会重复堆积，太紧会误杀。知乎那篇高赞答案给的默认思路：`ADD / UPDATE / DELETE / NOOP` 四算子，事实会变的场景用 **mark-invalid** 而不是物理删除。

**6. 成本护栏。** 后台捕获要能设上限：每会话最大抽取次数、单次最大输入 token、模型路由到便宜档。Hermes 的教训是"默认值在繁忙主机上会烧掉可观 token"。

**7. 注入仍然要管。** 召回 20 条塞进提示词是危险信号（知乎设计文的原话：**每轮都注入 20 条记忆就是危险信号**）。控制在 3–5 条。

## 八、开发流程（照 Amadeus 的做法）

这条路的风险不在"写代码"，在"被插件绑死 + 成本失控 + 数据被改坏"，所以流程要加三个门槛：

```
docs/research/
  01-provider-survey.md      ← 四个 DSH 插件的许可证 / peer / 依赖 / 成本模型
  02-trial-matrix.md         ← 每个装一次，同 30 条记忆 + 20 查询，记录命中率与延迟
  03-cost-model.md           ← 每会话 token 估算（抽取 + 嵌入 + 召回 + 注入）
  04-data-safety.md          ← 数据落地在哪、能不能导出、卸载后数据还在吗
  05-adr.md                  ← 决策记录：采用哪个、为什么
docs/audits/                 ← 每次升级插件后的回归记录
```

**必须验证的四件事**（否则不要上生产）：
1. **数据能导出**——卸载插件后记忆还在，且格式可读；
2. **能关掉自动整合**——只保留捕获；
3. **成本可估**——每会话 token 有数，不是"感觉还行"；
4. **许可证清楚**——尤其 `OpenViking`（AGPL）与 `WeKnora`（NOASSERTION）。

## 九、里程碑与验收

| 阶段 | 产出 | 验收标准 |
|---|---|---|
| M0（半天） | 选定一个候选（建议 MemOS 或 EverOS） | 许可证/peer/依赖三项通过 |
| M1（1 天） | 隔离环境装通 | DSH 里能看到插件工具；写入/召回各跑通一次 |

| M4（1 天） | 成本基线 | 一次会话的 token 消耗有具体数字 |
| M5（1 天） | 导出与卸载演练 | 卸载后数据完整可读；重新装回不丢 |
| M6（持续） | 回归 | DSH 或插件升级后跑一遍 M2 的查询集 |

## 十、风险、许可证与退出策略

| 风险 | 影响 | 应对 |
|---|---|---|
| **自动整合伤害效果** | 越用越笨（论文实测 100%→52.6%） | 关掉自动整合；只捕获不提炼；每条留 `source` |
| 成本失控 | 账单/配额 | 设抽取上限、路由便宜模型、监控每会话 token |
| **AGPL（OpenViking）** | 分发/服务化即触发 | 不选，或只做内部自用并接受约束 |
| **NOASSERTION（WeKnora）** | 授权不明 | 商用前书面核实 |
| 版本耦合 | DSH 升级集体失效 | 隔离 profile 试；保留回退 |
| 数据被改坏 | 不可逆 | 导出/备份先行；软删除 |
| 隐藏的托管默认 | 数据上云 | 例如 `claude-mem` 默认走托管，必须显式选本地 |

**退出策略**：**先写导出，再装插件**。如果它导不出可读格式，这条路径就不该选。

## 十一、结论

**这条路召回最强、自动化最高，也最容易反噬。**

它适合"记忆量确实大、需要语义召回、并且愿意为运维和 token 付账"的场景。对你现在的阶段（从零搭建个人工作台记忆），我的判断是：

**不要先做这条。** 先用路径 A 把"记什么、谁来确认、怎么注入"跑通，用路径 B 补上中文检索。等真的撞到"几十条记忆不够用"这堵墙，再引入路径 D——而且优先选**有官方 DSH 插件 + Apache-2.0 + 能导出**的那几个（MemOS / ReMe / EverOS）。

**如果一定要现在就上**，请守住三条底线：
1. **关掉自动整合**（论文的结论够清楚了）；
2. **每条记忆必须带 `source`**；
3. **先验证导出，再验证召回**。
