# 第一部分 · 补齐结构细节

## 一、`world fact` 与 `experience` 分离

### 1.1 为什么必须分开

现在 `MEMORY.md` 混着两类：

```
用户的项目 A 用 Axum + SQLx，构建命令 make dev          ← 世界事实
我上次按 README 装依赖失败：Node 18 不支持 node:sqlite   ← 自身经历
```

它们的**失效条件不同**：

| | 世界事实 `[fact]` | 自身经历 `[exp]` |
|---|---|---|
| 描述对象 | 外部世界的状态 | 我自己做过什么、结果如何 |
| 什么时候过期 | 外部变了（换框架、改命令） | 环境变了（换机器、换版本） |
| 过期后价值 | 归零，必须删 | **教训可留下**（升为 strategy 或保留为反例） |
| 谁最容易说错 | 模型推断（"应该是这样"） | 模型回忆（"我记得是那样"） |

混在一个文件里，**过期清扫无法区别对待**：要么把仍有价值的教训一起删掉，要么让过期事实长期污染检索。

### 1.2 磁盘格式（路径 A）

条目首部加类型前缀，**写入时必填**：

```
[MEMORY.md]

[fact] 用户项目 A 用 Axum + SQLx；构建 `make dev`；测试 `cargo nextest`
§
[fact] 校务系统登录入口 https://jw.example.edu.cn/sso，用学号 + 统一身份密码
§
[exp] 2026-10-14 按 README 装依赖失败：Node 18 不支持 node:sqlite；换 22.19 后成功
§
[exp] 2026-10-16 直接改 MEMORY.md 导致插件读不到，必须走 memory 工具
```

**规则**：

| 项 | 规定 |
|---|---|
| 前缀 | `[fact]` / `[exp]`，区分大小写，紧跟行首 |
| `[exp]` 日期 | **必须以 `YYYY-MM-DD` 开头**，否则拒绝写入（没有日期的经历无法判断时效） |
| `[fact]` 日期 | 可选 `verified:YYYY-MM-DD`，用于复审 |
| 未知前缀 | 读取时**宽容**（当作 `[fact]` 并标记 `untyped`）；写入时**严格**（拒绝） |
| 前缀后 | 一个空格，然后正文；正文不含独立 `§` 行（沿用原规则） |

### 1.3 注入格式

按类型分组，各给一个子标题，`[exp]` 额外标年龄：

```markdown
## MEMORY

### 世界事实
- 用户项目 A 用 Axum + SQLx；构建 `make dev`；测试 `cargo nextest`
- 校务系统登录入口 https://jw.example.edu.cn/sso，用学号 + 统一身份密码

### 自身经历（按时间倒序，超过 60 天的标记为「待复盘」）
- 2026-10-16 直接改 MEMORY.md 导致插件读不到，必须走 memory 工具
- 2026-10-14 按 README 装依赖失败：Node 18 不支持 node:sqlite；换 22.19 后成功
```

**为什么分组而不是每条带前缀**：前缀占 6–7 个字符 × 每个条目，在 10000 字符预算下是实打实的浪费。**磁盘用前缀（可解析），注入用分组（省 token）**——和 Amadeus"磁盘 `\n§\n`、注入加空行"是同一个思路。

### 1.4 容量配额

`MEMORY.md` 总量仍 10000 字符，但**加一条子预算**：

```
[exp] 条目合计 ≤ 40%（4000 字符）
```

**理由**：经历会自然堆积（每次干活都可能产生一条），而事实是有限的。不限流的话，几个月后文件里全是"我试过 X 失败"，把"用户是谁"挤出去。

超配额时：**拒绝新增 `[exp]`**，并在错误里提示"请先复盘并归档旧经历"，而不是静默淘汰。

### 1.5 衰减与清扫

| 类型 | 周期 | 动作 |
|---|---|---|
| `[fact]` | 90 天未复审 | 标注「待核实」，下次相关任务时优先校验；**不自动删** |
| `[exp]` | 60 天 | 转为「待复盘」：要么升为 `strategy`，要么归档到会话日志；**不静默删** |
| 任一类型 | 被明确证伪 | `status: retracted`，保留原文 + 证伪来源 |

**关键**：**没有"自动删除"这个动作。** 所有淘汰都是"降级 + 需人确认"，因为记忆是不可重建的（会话日志能重建索引，不能重建"当时我怎么想的"）。

### 1.6 工具 API 变更

`memory` 工具的三个写动作**新增必填参数 `kind`**：

```json
{ "action": "add", "target": "memory", "kind": "fact", "content": "..." }
{ "action": "add", "target": "memory", "kind": "exp",  "content": "2026-10-16 ..." }
```

- `target: "user"` 不接受 `kind`（用户画像天然是 fact 类）；
- `replace` 允许改 `kind`，但改类型视同"删旧建新"，要留审计；
- `query` 可选按 `kind` 过滤。

**硬化落点**：`kind` 校验在**服务端**（见 [06](06-约束硬化设计.md) L1），不是工具层——否则注入一个工具就能绕过。

### 1.7 迁移

存量条目无前缀 → 一次性迁移脚本按启发式分类（含日期 + 第一人称 + "失败/成功/试过" → `exp`；其余 → `fact`），**结果写进审计并要求人工抽查**。不要指望模型自动分类，它会全部标成 `fact`。

## 二、`strategy` 层（现在完全缺失的中间层）

### 2.1 三层定位

```
case       会话日志 + 历史检索        "那天发生了什么"     已有
strategy   从多条 case 提炼的判断     "这类问题通常先查 X"   ← 缺这一层
skill      可执行步骤（SKILL.md）      "照着这七步做"        已有
```

**strategy 与 skill 的边界**（最容易混）：

| | strategy | skill |
|---|---|---|
| 内容性质 | **判断、优先级、适用条件、反例** | **可执行步骤、命令、代码** |
| 形态 | 一段带证据的断言 | 一个流程 |
| 何时用 | 决定"先做什么、可信度多少" | 决定"具体怎么做" |
| 能否被引用 | 是（skill 可引用 strategy id） | — |
| 触发 | 按需检索，**不进常驻注入** | 按需加载 |

**举例**：strategy = "在 Windows 上装 Node 原生模块前，先确认 Python 与 Build Tools——过去两次失败都源于此"；skill = "Windows 原生模块安装检查清单（7 步）"。前者帮你**判断要不要先检查**，后者告诉你**怎么检查**。

### 2.2 存储格式

一条 strategy 一个文件（便于 diff 与评审）：

```
<memory.home>/strategy/
├── stg-0001.md
└── stg-0002.md
```

```markdown
---
id: stg-0001
claim: Windows 上安装 Node 原生模块前，先确认 Python 3 与 VS Build Tools
scope: env:windows
kind: precondition
evidence:
  - mem:exp-0014
  - mem:exp-0021
  - session:2026-10-14-node-sqlite
confidence: 2                 # 1=观察 2=模式 3=规律
status: active                # active | contested | retired
created_by: human             # human | distill-confirmed
created_at: 2026-10-17
last_validated: 2026-10-17
counterexamples: []
---

## 适用
Windows + 需要编译原生模块（node-gyp / better-sqlite3 / node:sqlite 的某些版本）。

## 不适用
纯 JS 包；或使用预编译二进制（prebuild-install 命中）时无需检查。

## 怎么做
1. `python --version` 存在且为 3.x
2. `npm config get msvs_version` 有合理值，或装有 VS Build Tools
3. 再执行 `npm install`

## 依据
2026-10-14 与 2026-10-16 两次失败均为此原因；第三次先检查后一次通过。
```

### 2.3 生成门槛（这是整套设计里最关键的一条）

**strategy 不能自动生成。** 理由是已核实的研究结论（[arXiv 2605.12978](https://arxiv.org/abs/2605.12978)）：连续自动整合会让准确率从 100% 掉到 52.6%，主要失效模式正是"**分错组、丢条件、小场景被说成大规律**"——而 strategy 恰好就是"把若干 case 说成规律"的那一步。

**允许的两条生成路径**：

| 路径 | 触发 | 约束 |
|---|---|---|
| 人工 | 直接编辑文件 / `/strategy new` | 无额外约束 |
| **确认式蒸馏** | `/distill <exp-id>...`，模型产出草稿，**人确认**后才落盘 | 见下 |

**确认式蒸馏的硬约束**（服务端校验，不靠提示词）：

1. **证据 ≥ 2 条，且来自不同会话**（同一会话里的两条不算——那可能只是同一上下文里的重复观察）；
2. 每条证据必须是已存在的 `[exp]` 条目 id，**不能引用不存在的条目**；
3. `created_by: distill-confirmed`，且审计里记下确认时间与确认人；
4. **`confidence` 由系统算，模型不得填写**（见 2.4）；
5. 正文必须包含"适用"与"不适用"两节，缺一拒绝——**没有边界的规律就是偏见**。

### 2.4 置信度：由证据算，不由模型评

```
confidence = 1  若 证据数 == 1                     （观察）
           = 2  若 证据数 >= 2 且 会话数 >= 2      （模式）
           = 3  若 证据数 >= 3 且 会话数 >= 3 且 无反例  （规律）
反例存在 → status: contested，confidence 冻结在 1
```

**为什么必须这样**：让模型给自己的归纳打分，等于让它给幻觉盖章。这和我上一轮说的"beliefs 的 confidence 只能由证据计算"是同一条原则。

### 2.5 反例与退役

- 每次 `[exp]` 写入时，顺手做一次**反例匹配**（按 `scope` + 关键词），命中则提示"可能构成 stg-0001 的反例"；
- 反例经人确认后写入 `counterexamples`，`status` 转 `contested`；
- `contested` 超过 30 天未处理 → 降级 `retired`（**不是删除**，保留可查）；
- `retired` 的 strategy **不参与检索默认结果**，但可显式查。

### 2.6 加载方式：不进常驻注入

**strategy 绝不放进系统提示词。** 理由：它数量会增长、且只在特定任务有用；常驻注入会重演"每轮注入 20 条记忆"的错误（知乎那篇设计文的原话就是危险信号）。

**改为按需**：

```
strategy_search(query, scope?) → 返回 top-3 的 {id, claim, confidence, status}
strategy_read(id)              → 完整正文
```

主 agent 在开始一个可能重复的任务前调 `strategy_search`；命中且 `confidence >= 2` 才建议采纳。

### 2.7 容量与清扫

- strategy 总量上限：**50 条**（超过说明你在囤积而不是提炼）；
- 每条正文 ≤ 2000 字符；
- 90 天未命中检索 → 标 `dormant`，提示合并或退役。

## 五、驳回的四处

### 5.1 "感官 / 短期 / 中期 / 长期"四层：不建议采用

- **感官记忆**：原文定义为"存储原始输入、瞬时缓存、快速过滤噪声"。工程上没有对应物——原始输入本来就在会话日志里，多造一层只会多一次拷贝。
- **中期记忆**：原文定义为"会话级归档，按天/按任务组织"。这对我们**就是会话日志 + 历史检索工具**，已经是现成的，不需要新层。
- 真正有区分度的只有 **working**（上下文内）和 **persistent**（跨会话）。我们已经有这条线（上下文 vs `MEMORY.md`）。
- 额外三层会带来**三套淘汰规则**，而你根本无法判断"一条记忆该进中期还是长期"——这是典型的"分层好看但没人会正确使用"。

**我们的分层已经够用**：`会话日志(case)` → `[fact]/[exp]` → `strategy` → `skill`。这是**按抽象层级分**，比"按时间长度分"可操作得多。

### 5.2 LangChain 代码已过时（会直接报错）

| 原文写法 | 现状 |
|---|---|
| `from langchain.chat_models import ChatOpenAI` | 已移到 `langchain_openai`；旧路径在新版本不可用 |
| `ConversationSummaryBufferMemory` | 在较新 LangChain 中已废弃/移除 |
| `ChatOpenAI(model_name="gpt-3.5-turbo")` | 模型本身已过时 |
| `vectorstore.persist()` | Chroma 新版本自动持久化，该方法已移除 |

### 5.3 对 OpenClaw 的描述与官方文档有出入

| 原文说法 | 官方文档口径（我此前抓取） |
|---|---|
| "OpenClaw 四层记忆架构：工作/短期/长期/**检索加速层**" | 官方描述的是 **`USER.md` + `MEMORY.md` + `memory/YYYY-MM-DD.md` + `DREAMS.md`** 四个文件，加上 Builtin(SQLite) 检索引擎。**"检索加速层"不是一个记忆层**，是引擎能力 |
| "短期记忆：自动压缩摘要，**降低 Token 90% 以上**" | 无此数据。官方讲的是 MEMORY.md 超预算时**磁盘不动、只截断注入副本** |
| "**Silent Memory Flush**：静默提取并写入 MEMORY.md" | 接近但不同：官方是**压缩前跑一个静默 turn 提醒 agent 保存**，不是自动提取直写 |

**这条差别很重要**：原文把 OpenClaw 描述成一个"自动静默写记忆"的系统，而官方文档和我此前核实的多份材料（含 Hermes 的 `write_approval`、dsh-memento 的审批门）都指向**"自动捕获要有门"**。别照着这篇文章去实现一个静默自动写入。

### 5.4 示例代码的三处技术错误

如果直接抄它的 SQL，会出现**索引与数据不一致**：

**错误 1 · FTS5 external-content 的 UPDATE 触发器写法错**

原文：
```sql
CREATE TRIGGER chunks_after_update AFTER UPDATE ON chunks
BEGIN
  UPDATE chunks_fts SET text = new.text WHERE rowid = new.id;   -- ❌
END;
```
external content FTS5 **不支持**直接 UPDATE 内容列。正确写法是先删后插（或用 `'delete'` 命令）：
```sql
INSERT INTO chunks_fts(chunks_fts, rowid, text) VALUES('delete', old.id, old.text);
INSERT INTO chunks_fts(rowid, text) VALUES (new.id, new.text);
```
按原文写法，更新后的文本在全文索引里会**依然检索到旧内容**。

**错误 2 · 缺少 DELETE 触发器**，删除记忆后索引残留。

**错误 3 · 向量写入类型不对**

原文：`INSERT INTO chunks_vec(rowid, embedding) VALUES (new.id, json_extract(new.embedding,'$'));`

`json_extract(...,'$')` 返回的是 **JSON 文本**，而 `vec0` 期望的是**紧凑的 float32 二进制块**（或按其版本规定的数组形式）。直接塞文本会报错或写入垃圾。同时把 embedding 以 JSON TEXT 存在 `chunks` 里再抽出来，本身也是冗余。

**顺带**：这套 SQL 没有 `schema_version`、没有事务边界说明、去重也没有按作用域隔离。

## 六、可用的四条

### 6.1 MMR 去重（我们完全没有）

> 原文："采用 MMR（最大边际相关性）算法去重，避免召回内容冗余"

**这是个真缺口。** 我们的检索目前会返回 top-k，但没有任何机制阻止"5 条几乎一样的记忆"占满名额——尤其 `[exp]` 类条目，同一件事反复踩坑就会产生多条近似记录。

**落地**（路径 B 混排阶段）：
```
1. 先按混合分数取 top-3k
2. MMR 迭代选择：score - λ * max_sim(已选)
   λ = 0.7（越接近 1 越强调多样性）
3. 截到 top-k
```

### 6.2 时间衰减半衰期

> 原文："结合时间衰减（30 天半衰期），新记忆权重更高"

我们已经讨论过"陈旧清扫"，但**清扫是离散的（过期/不过期），衰减是连续的**——两者互补。落地为打分项：

```
final = 0.6 * relevance + 0.25 * recency + 0.15 * confidence
recency = 0.5 ** (age_days / 30)
```

**但 `[fact]` 与 `[exp]` 要用不同半衰期**：事实 90 天，经历 30 天（经历衰减更快）——这正是第一部分拆开 types 的收益。

### 6.3 压缩提示词模板（改比例后用）

原文给的模板可用，但**"压缩到 10–15%"这个目标与已核实论文冲突**（过度压缩的失效模式正是"丢条件"）。改为：

```text
你是记忆压缩助手。对给定对话做无损优先的压缩：
1. 必须保留：用户明确给出的规则、格式、参数、路径、数值、期限；
2. 必须保留：用户说的"不要/禁止/必须"类约束，逐字保留，不得改写；
3. 必须保留：决策及其理由（一句话即可）；
4. 可以丢弃：寒暄、重复表述、中间试错过程（但若试错揭示了坑，保留结论）；
5. 输出为条目列表，每条一个事实，不超过 40 字；
6. 不确定是否重要时，保留而不是丢弃；
7. 不添加原文没有的推断。
目标压缩率 30–50%，不要追求更小。
```

**第 2 条和第 6 条是关键**——论文里"小场景被说成大规律"就是从改写用户的限定条件开始的。

### 6.4 "记忆注入"作为一等能力

原文把"记忆注入"单列为五项核心能力之一。**这个切法值得学**：注入不是"检索的自然延伸"，它有独立的策略（注入什么、注入多少、什么格式、何时刷新、是否冻结）。

我们其实已经在做（分段注入、冻结快照、`## MEMORY` 标题、字节稳定），但从没把它**当一层来设计**。补一条检查：**注入层应当有独立的配置与独立的测试**（比如"同一会话内注入文本字节不变"就该是一个测试用例）。

# 第三部分 · 第二篇 CSDN 文章评估（`163050919`）

> **原题**：《AI Agent 为什么会"失忆"？从 0 到 1 详解生产级四层 Memory 记忆架构设计》（2026-07-20）
> **总评**：**比上一篇明显靠谱，但整体是"多租户 SaaS"架构，与单用户本地场景错配。** 可用 3 条 + 1 个方法论优点；有 3 处与已验证结论冲突。

## 九、值得肯定的四处

**1. 概念的讲法准确。**
"LLM 是纯函数（stateless），你在 ChatGPT 里感受到的连续对话，是**应用层每次都把历史重新拼进 prompt**——模型没有记忆，是你的应用在替它背稿子。" 这个表述比多数同类文章清楚。

Context vs Memory 的对照表也站得住（临时输入 vs 持久状态、注意力窗口 vs 外部存储、按次计费 vs 存储成本）。**"长上下文 ≠ 记忆"** 与我们的判断一致。

**2. 引用了一处可核实的权威来源。**
它说"OWASP 已把 Memory Poisoning 列为 Agent Top 10 安全风险之一"——**这条是对的**。OWASP GenAI Security Project 于 2025-12 发布 [Agentic AI Top 10 Risks and Mitigations](https://genai.owasp.org/2025/12/09/owasp-genai-security-project-releases-top-10-risks-and-mitigations-for-agentic-ai-security/)，其中 **ASI06 = Memory and Context Poisoning**。另有专文 [《Memory Is a Feature. It Is Also an Attack Surface》](https://genai.owasp.org/2026/05/13/memory-is-a-feature-it-is-also-an-attack-surface/)。

**这条应当补进我们的安全章节**——我此前只从 Hermes 的实现里推断"要扫描"，现在有了可引用的标准出处（见第十节）。

**3. 优化效果表没有编数字。**
第七节写"具体数值因业务而异，下表为典型场景下的量级对比，**仅供参考**"，表里只给箭头（⬇️/⬆️），并补一句"建议以自身压测数据为准"。

**对比上一篇直接写"降低 90%""准确率 +26%"——这种"只给方向、标注不确定"的写法应当被肯定，也值得我们自己写文档时照做。**

**4. "双缓冲"给了我们缺的一个名字。**
短期记忆层要求：一个**不可变的 `System Base`**（系统提示词等核心指令永久保留）+ 一个**可滑动的 `History Window`**。

这正是 `billion-context-dsh` 撞过的那个问题（压缩掉 `AGENTS.md` 当前副本 → 宿主重注入 → 死循环），也是我上一轮说的"约束不能住在上下文里"。**它给出了一个可直接落地的结构名**，见第十节。

## 十、可以拿走的三条

### 10.1 不可变区（immutable region）—— 这条要立刻补进设计

把上下文划成两个**物理隔离**的区域：

```
不可变区（任何压缩/滑动/重写都不得触及）
├── 系统提示词固定开场
├── MEMORY / USER 注入段
├── MEMORY_GUIDANCE / AGENTS.md 当前副本
└── 工具定义

可变区（可压缩、可滑动、可摘要）
└── 对话轮次、工具结果、中间结论
```

**与已有结论的关系**：`billion-context-dsh` 的"注入行卫生"是这条的**应急补丁版**（压缩时拒绝覆盖注入行）；这里是**结构性版本**——不是"压缩时小心别碰"，而是"它根本不在可压范围里"。

**落地要求**（写进路径 A 与 06）：
- 注入段的 seq 范围必须被标记为 `protected`；
- 任何压缩请求若覆盖 `protected` 范围 → **硬拒绝并点名可重切的区间**；
- 测试断言：压缩 20 次后，注入段字节不变。

### 10.2 HyDE（可选，个人场景慎用）

先用 LLM 生成一段"假设性答案"，再用它去检索向量库，提升模糊查询的命中率。

**判断**：技术上成立，但**每次查询多一次 LLM 调用**。对单用户个人记忆（条目几十到几百条）来说，收益不抵成本；**只在路径 D 且查询确实模糊时考虑**，不要默认开。

### 10.3 RRF 融合 + 时间衰减奖励（补齐我们的融合算法）

我们前面只写了 MMR 去重与衰减打分，**没写多路结果怎么融合**。它的骨架是对的：

```
score[id] += 1 / (rank + 60)          # 经典 RRF，k=60
if age > 7d: score[id] *= 0.8         # 新鲜度奖励
```

**改进**：`*0.8` 这种阶梯折扣不如**连续衰减**（我们已定的 `0.5 ** (age/half_life)`），且要和 `[fact]`/`[exp]` 不同半衰期配合。**采用 RRF 形式 + 我们的衰减函数。**

顺带指出一个 bug：示例里 `final_scores[res.id] += ...` 在字典键不存在时会 `KeyError`，应为 `final_scores[res.id] = final_scores.get(res.id, 0) + ...`。

## 十一、三处与已验证结论冲突

### 11.1 「元记忆」自动提炼技能 + 参数自调优 → 不接受

原文第四层元记忆做四件事，其中两件是：

> "**技能提炼**：把连续成功的操作路径抽象成可复用的 Skill……下次遇到类似问题直接调用，不再走完整思考链"
> "**参数自调优**：……发现滑动窗口频繁爆满，自动把窗口从 10 轮调成 8 轮"

**这和我上一轮核实的论文直接冲突**（[arXiv 2605.12978](https://arxiv.org/abs/2605.12978)：连续自动整合 10 轮后准确率 100%→52.6%，失效模式正是"把若干案例说成规律"）。

我们的立场不变：**strategy 只能人工或"确认式蒸馏"产生**（见第二部分 2.3）；**参数自调优更危险**——它会让系统在无人察觉时改变自身行为阈值。

**但元记忆的另一半可以留**：冲突检测 + 告警（"生产环境必须有人工在环"这句它写对了）。我们已经有"反例匹配"，只是缺"定期扫描告警"。

### 11.2 「事实核查：置信度低于 0.7 就丢弃」→ 方法可疑

> "写入前过一道轻量级 LLM 做事实性幻觉检测，置信度低于阈值（如 0.7）宁可丢弃也不写入"

**问题**：让同一个模型给自己刚产生的陈述做幻觉检测，效果有限；而且 0.7 这个阈值没有依据，**由谁校准也没说**。

**我们的替代方案**更硬：写入前做**确定性扫描**（凭据特征、不可见 Unicode、注入模式——见 06 的 L1），而不是让模型自评。**可验证的规则优先于模型的自我评估。**

### 11.3 「主动硬删除」→ 与我们冲突

> "**主动删除**：被判定为错误/敏感/过时的记忆，硬删除或加软删除标记"

**我们不做硬删除。** 理由在 08 第一部分 1.5 已写：记忆不可重建（会话日志能重建索引，不能重建"当时我怎么想的"）。淘汰一律是"降级 + 留痕"。

## 十二、为什么它的四层不能照搬

**先看一个现象**：两篇 CSDN 文章都叫"四层架构"，但层完全不同——

| 上一篇（163697532） | 本篇（163050919） |
|---|---|
| 感官 / 短期 / 中期 / 长期 | 工作 / 短期 / 长期 / **元记忆** |

**"四层"是一个流行模板，不是共识。** 这本身就说明：不要因为层数整齐就照抄。

**再看它的栈**：Milvus + Neo4j + PostgreSQL + Redis + Elasticsearch + S3 Glacier。

这是**多租户生产 SaaS** 的配置（它自己也承认"MVP 阶段可以只用 PostgreSQL 一把梭"）。对单用户本地记忆：

- 装 4 个服务 = 4 个故障点、4 套备份、4 处版本升级；
- "冷数据归档到 S3 Glacier"在本地场景无意义；
- 它的"长期记忆"设计针对的是**海量非结构化片段检索**，而你的记忆是**几十到几百条精炼条目**——问题规模差三个数量级。

**结论**：它的**分层思想可读**，**栈不可抄**。
