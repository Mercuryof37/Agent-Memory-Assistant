# 11 · 收尾蒸馏（Closeout Distillation）机制设计

> **用户方案**：宣布项目/阶段结束时 → 提示 Agent 总结本阶段问题 → 分条列出可写入的约束条件 → 由人决定采纳哪些 → **不自动注入**。
> **我的判断**：**骨架正确，三处要改**——触发点太少、证据来源不对、输出类型混在一起。下面是改进后的完整机制。

---

## 一、你的方案哪里对（先说这个）

| 你的设计 | 为什么对 |
|---|---|
| **由人决定采纳哪些** | 直接对应已核实的论文结论：连续自动整合 10 轮后准确率 100%→52.6%。**人做最后一道闸，是唯一被证据支持的形态** |
| **不自动注入** | 踩坑条目会持续增长，自动注入几个月就吃掉全部预算；按需检索才对 |
| **分条列出，而不是一段总结** | 条目化才可逐条采纳/否决/追溯；一段散文只能"全收或全丢" |
| **以"阶段结束"为触发** | 这个时刻上下文还热、你的记忆还清楚、返工代价刚发生——**比随机时机好得多** |

**骨架不用改。** 下面三处是补强。

---

## 二、三处要改

### 改动 ①：触发不能只有"项目结束"——太晚、太粗、会漏

**问题**：

1. **太晚**：成本浪费、错误返回这类事**发生时就该记**。等到项目结束，中间可能已经压缩过两三次，你总结的其实是"摘要的摘要"——这正是论文里的失效模式。
2. **太粗**：小任务不会有"结束"这个动作，它们永远不被复盘。
3. **不可靠**："宣布结束"依赖你记得说；忘了就没有。

**改法：三级触发，成本递增**

| 级别 | 触发条件（确定性，不靠模型判断） | 动作 | 成本 |
|---|---|---|---|
| **L0 打标** | 同一错误重复 ≥2 次 / 工具连续失败 / 用户纠正语（"不对""我说过""别再"）/ 回滚 / 单轮 token 异常 | **只打标 + 保存原始片段指针，不生成任何文字** | ≈0 |
| **L1 收尾** | 你说"这个项目先到这""今天收工" / `/closeout` / 任务完成事件 | 汇总所有未处理标记 + 扫原始存档 → 产出提案 | 一次 LLM 调用 |
| **L2 补漏** | 累积 ≥N 条未处理标记，或距上次 ≥7 天 | 批量蒸馏 | 低频 |

**关键在 L0**：它便宜、确定性、不依赖模型"觉得该记"。**打标只存指针，不写文字**——真正的生成推迟到 L1，那时才花 token。

### 改动 ②：证据必须来自原始存档，不能来自"当前上下文"

**问题**：L1 那一步如果让 agent"回忆本次开发过程"，它回忆的是**已被压缩过的上下文**。压缩会丢条件——论文里"小场景被说成大规律"就是这么来的。

**改法**：

```
L1 蒸馏的输入 = archive/sessions/ 的原始片段 + L0 标记的指针
禁止输入 = 当前会话上下文（可能已被摘要）
```

所以 10 里"**先落原始轨迹，再蒸馏**"不是可选项，是这套机制的前提。顺序反了，蒸馏出来的东西不可信。

**并且每条提案必须带原文引用**（≤200 字），否则不予受理——**没有引用的提案 = 模型的印象**。

### 改动 ③：输出不能全是"约束"——要分四型，各走各的路

**问题**：你举的两个例子里，"不必要的开发成本增加"和"未验证的错误返回"**不是同一类东西**：

- 前者是**流程判断**（"先跑通最小验证再扩展"）——无法写成测试
- 后者是**可执行规则**（"声明完成前必须跑通一次成功路径"）——能写成检查

如果都塞进 `RULES.md`，结果是**规则里混满无法检验的散文**，最后没人看。这正是我们 08 里说的"没有边界的规律就是偏见"。

**改法：四型分流**

| 类型 | 是什么 | 去哪 | 硬性要求 |
|---|---|---|---|
| **`rule`** | 可执行的禁止/必须 | `RULES.md`（T2） | **必须能写出一个会失败的测试**，否则降级 `pitfall` |
| **`pitfall`** | 情境性事实（这个库/这台机器/这个版本） | `memories/pitfall/`（按需检索） | 必须带 `error_signature`（便于触发式提示） |
| **`strategy`** | 跨项目可迁移的判断 | `strategy/`（人工确认） | **≥2 条跨会话证据**，且必须写"不适用"场景 |
| **`process`** | 流程改进（更像习惯） | `USER.md` 或 `RULES.md[软]` | 标注 `[软]`，明示不可检验 |

## 三、完整机制：收尾蒸馏

### 3.1 流程

```
项目/阶段结束（你宣布 或 /closeout）
        ↓
[系统] 冻结本会话 → 归档原始轨迹（若未归档）
        ↓
[系统] 汇集本次所有 L0 标记 + 扫描存档中的失败/纠正片段
        ↓
[Agent] 在受限 schema 下产出提案（≤7 条），每条带原文引用
        ↓
[系统] 校验：类型合法 / 有引用 / rule 有 check / strategy 有 ≥2 证据 / 不与既有重复
        ↓
[你] 一屏表格逐条决定：采纳 / 延后 / 否决
        ↓
[系统] 采纳 → 按类型落库（rule 必须同时建检查）
        ↓
[系统] 否决 → 写入 rejected.jsonl（附理由），以后不再提
```

**注意第 2 步和第 6 步都是"系统"做的**，不是靠提示词。这与你上一轮的要求一致：**触发与校验是门禁，不是宪法**。

### 3.2 提案 schema（受限输出）

```json
{
  "proposals": [
    {
      "id": "p-001",
      "type": "rule",
      "claim": "声明'已完成'之前，必须实际执行一次成功路径",
      "scope": "local",
      "evidence": [
        { "session": "2026-10-14-api", "seq": 412,
          "quote": "我改好了，应该可以了（未运行）" }
      ],
      "cost": "返工约 40 分钟；且你误以为已通过",
      "check": "closeout 前跑 scripts/smoke.sh，失败则不得声明完成",
      "falsifier": "若改动仅为文档/注释，则无需运行",
      "confidence": 2,
      "suggest": "adopt",
      "dupe_of": null
    }
  ],
  "considered_and_rejected": [
    { "claim": "不要用 tab 缩进", "reason": "项目已统一 prettier，重复且不可检验" }
  ]
}
```

**硬性校验（服务端做，不合格直接退回）**：

| 校验 | 不通过的处理 |
|---|---|
| `type` ∈ 四类 | 退回 |
| `evidence` 非空，且每条有 `session`+`seq`+`quote` | 退回 |
| `type=rule` 必须有 `check` | 退回（或降级为 `pitfall` 后重提） |
| `type=strategy` 必须有 ≥2 条**不同会话**的证据 | 退回 |
| 提案总数 ≤7 | 超出的截断并告知 |
| 与既有 `RULES.md` / `pitfall` / `rejected` 重复 | 标 `dupe_of` 后剔除 |

**为什么要设 ≤7**：这是**强制排序**。不设上限，模型会提 20 条，你只会全选或全不看——两种都等于没做。

### 3.3 你的决定界面（关键是"便宜"）

一屏表格，**默认全不采纳**：

```
#   类型      一句话                                   代价          建议   [ ]
p1  rule      声明完成前必须真跑一次成功路径           返工40min     采纳
p2  pitfall   node-sqlite 在 Node18 下静默失败        白折腾1h      采纳
p3  strategy  原生模块问题先查工具链再查代码           两次踩坑      延后
p4  process   先打最小样再抽抽象层                     多写200行     采纳
```

- **一行一句话**，细节展开才看证据；
- 每行显示**代价**——你决策靠的是代价，不是模型的说服力；
- **采纳 `rule` 时，系统要求填 `check`**；填不出 → 自动降级为 `pitfall`（防止规则里混散文）；
- 采纳后**立刻可见效果**：`rule` 进 `RULES.md` 并生成测试骨架；`pitfall` 进库并带签名。

### 3.4 否决要留痕（否则会反复提）

```
archive/proposals/rejected.jsonl
{"claim":"不要用 tab 缩进","reason":"prettier 已统一","at":"2026-10-17"}
```

下次蒸馏时，模型**先读这个文件**，不得重提已否决项。否则每次收尾都弹同样的三条，你会开始无脑点"否决"，闸门失效。

## 四、我另外建议的两条（你没提，但我认为必要）

### 4.1 踩坑的"触发式提示"：按需出现，而不是完全不出现

你说"不自动注入"——对。但**不注入 ≠ 找不到**。

如果踩坑只存在库里、靠你主动问，那它永远用不上（你不会在报错时想"我该问问记忆"）。

**建议**：给每条 `pitfall` 加 `error_signature`（报错文本的正则/关键词）：

```yaml
error_signature: "gyp ERR!|node-gyp|MSB\\d+|prebuild-install"
```

**工具调用失败时，服务端拿 stderr 去匹配**，命中就附一行提示：

```
（可能相关）P12：上次同样报错是 Node 18 不支持 node:sqlite。
```

这是"不自动注入"的正确形态：**不是不出现，而是只在证据命中时出现一行**。既不占常驻预算，也不会被忽略。

### 4.2 采纳之后要有闭环：规则会不会烂掉

一条 `rule` 采纳后如果没人引用、没测试跑，三个月后它和不存在一样。

**建议三个观测**：

| 观测 | 动作 |
|---|---|
| 每次 `rule` 被注入 / 被违反，记审计计数 | 能回答"R3 到底有没有用" |
| 30 天从未被引用的 `rule` | 提示复核（可能过细，可合并或降级） |
| 被违反且造成实际返工的 `rule` | 提示把 `[软]` 升级为带测试的 `[硬]` |

## 五、和你方案的对照

| 环节 | 你的方案 | 改进后 |
|---|---|---|
| 触发 | 项目结束时 | **三级**：L0 确定性打标（零成本）+ L1 收尾 + L2 补漏 |
| 生成时机 | 收尾时生成 | **L0 只打标存指针，L1 才生成**（避免"摘要的摘要"） |
| 证据 | 隐含"凭回忆" | **必须引用 archive 原文片段**，否则退回 |
| 输出 | "约束条件"一种 | **四型分流**：rule / pitfall / strategy / process |
| 数量 | 不限 | **≤7**，强制排序 |
| 决定 | 你决定 | 你决定 + **默认不采纳 + 显示代价 + rule 必须配 check** |
| 否决 | 未提 | **写入 rejected.jsonl，不再重提** |
| 事后可用 | 不自动注入 | **不注入，但按 error_signature 触发式提示一行** |
| 事后监管 | 未提 | **引用/违反计数 + 30 天未用提示复核** |

## 六、落进 v1 的位置

这条机制属于 **v1 的 M3.5（在工具与权限之后、索引化注入之前）**，因为它依赖：

- `archive/sessions/`（M1 已有）
- 提案/决定的三档权限（M3 已有）
- 审计表（M1 已有）

**新增工作量估计 2–3 天**：

| 子项 | 估时 |
|---|---|
| L0 打标（错误重复、纠正语、工具失败检测） | 0.5 天 |
| L1 蒸馏 + schema 校验 | 1 天 |
| 决定界面（命令行表格即可，不必 Web） | 0.5 天 |
| `rejected.jsonl` + 去重 | 0.5 天 |
| `error_signature` 匹配提示 | 0.5 天 |

## 七、一句提醒

**这套机制最大的风险不是"做得不好"，而是"收尾变成负担"。**

如果每次收尾都弹 7 条、每条要读三段，你第三次就会开始跳过它。所以三个设计约束要守住：

1. **一行一句话，代价优先**——决策靠代价，不靠说服；
2. **默认不采纳**——不做任何事是安全的默认值；
3. **没东西可提时，明确说"本次无新提案"**——不要为了凑数而生成。**空结果是被允许的，也是常见的。**
