# 10 · 架构决策记录（ADR）与 v1 规格

> **输入**：用户对四问的回答 ——
> ① 记忆装：人格 + 偏好 + 使用约束 + 踩坑总结；
> ② 只给 DSH 用，但要留出路径 C（跨客户端共享）的接口；
> ③ 暂不做付费功能，但实现时要调研付费升级可能性、留出接口；
> ④ 愿意写插件。
>
> **结论**：**选路径 A 为主体，v1 只做文件型记忆；C 与付费能力以"接口 + 空实现"的形式预留，不实现。** 路径 B/D 暂不进入 v1。

---

## 一、四个答案各自改变了什么

| 回答 | 直接推论 |
|---|---|
| ① 人格+偏好+约束+踩坑 | **规模是几十到一两百条，不是几千条** → 不需要向量检索（否掉路径 D 的入场理由）；主要矛盾从"检索"变成"**容量与分层**"；内容天然分四类，需要分别处理（见第二节） |
| ② 只用 DSH，留 C 接口 | **服务层与适配器层从第一天就分开**；MCP 将来只是一个薄适配器，不是重写 |
| ③ 不做付费，留升级接口 | 数据模型**不写死单用户假设**；预留三个 hook，v1 全是 no-op；**不实现**多租户、计费、配额执行 |
| ④ 愿意写插件 | 自研可行；`memory-core` 可以做成纯逻辑包，独立单测 |

**一句话**：你的需求是"**小而精、强约束、可审计**"，不是"大而全、高召回"。这个定位决定了后面所有取舍。

## 二、内容分四类，必须分开处理（这是 Q1 的直接后果）

你说"人格 + 偏好 + 使用约束 + 踩坑总结"——**这四类东西的写入权、失效规律、注入方式全都不同**，混在一起就是设计事故。

| 类 | 载体 | 谁写 | 注入 | 失效 | 备注 |
|---|---|---|---|---|---|
| **人格** | `SOUL.md`（散文） | **人**（agent 无入口） | 摘要常驻 | 几乎不变 | agent 不得改，也不得"记住"人格 |
| **偏好** | `USER.md`（条目） | T0 可写 | 常驻全文 | 被新偏好取代 | 短、少、稳定 |
| **使用约束** | **`RULES.md`（编号）** | **人（T2）** | 常驻，带编号 | 显式废止 | ⚠️ **见下节，这是最关键的分流** |
| **踩坑总结** | `memories/pitfall/<name>.md` | T1 提案确认 | **按需** | `invalid_at` 或升 strategy | 最会长的一类，必须隔离在注入之外；**采集机制见 [11-收尾蒸馏机制设计.md](11-收尾蒸馏机制设计.md)** |

**"踩坑"为什么必须按需注入**：它会持续增长（每次踩坑都可能加一条），而且**绝大多数轮次用不上**。放进常驻注入，几个月就会吃掉全部预算——这正是我们在 `[exp]` 上加 40% 子预算的原因。

## 三、关键分流：「使用约束」不能当记忆存

这是本文最重要的一条。

你说要装"使用约束"。如果把它写成一条记忆（"不要用 sudo 跑 Docker"），那么：

- 它只是**提示词里的一句话**；
- agent 可以忽略、可以改写、可以在压缩中丢掉；
- 出了事你无法证明"它当时看没看到"。

**按 06 的结论，这类东西必须硬化。** 所以分成两半：

| | 软约束 | **硬约束** |
|---|---|---|
| 例子 | "回复用中文""文档多用例子" | "不要用 `sudo` 跑 Docker""不许把密钥写进记忆""改记忆前必须先读" |
| 载体 | `USER.md`（偏好） | **`RULES.md`，每条带编号** |
| 写入权 | T0 | **T2（只有人能改）** |
| 执行 | 靠提示词 | **代码/测试 + 服务端校验** |
| 注入 | 随偏好段 | **独立段，带编号 `R1/R2…`** |
| 可审计 | 否 | **是：日志记"本轮引用了 R3"，违反可定位** |

**`RULES.md` 的规格**：

```markdown
## RULES

R1 [硬] 不要用 sudo 执行 docker 命令；用户已在 docker 组。
R2 [硬] 记忆写入必须走 memory 工具；禁止用 write/edit 直接改 MEMORY.md。
R3 [硬] 凭据、密钥、token 一律不入记忆；检测到即拒绝写入。
R4 [软] 回复使用中文；代码与命令保持原样。
```

- 编号稳定，不复用（废止的留空号）；
- `[硬]` 条目**在代码里有对应校验或测试**，否则降级为 `[软]`（见 06 第四节的原则）；
- agent **没有**任何能改 `RULES.md` 的工具；只能人改文件或执行显式命令；
- 注入时**逐条列出**，便于审计引用。

**这条分流直接解决了你上一轮的顾虑**：约束不再是"Agent 可选择绕过的宪法"，而是有编号、有校验、有审计的系统设定。

## 四、架构：三层 + 两个预留适配器

```
packages/
├── memory-core/        纯逻辑，零 DSH 依赖，可独立单测
│   ├── store/          文件读写、原子替换、写锁
│   ├── index/          可重建索引（FTS5 / 内存），启动时校验
│   ├── rules/          RULES.md 解析 + 编号校验
│   ├── policy/         容量、层级、权限档位判定
│   ├── audit/          追加写审计（含被拒绝的写入）
│   └── service/        MemoryService 接口实现（C 路径的唯一入口）
├── memory-dsh/         DSH 适配器（v1 唯一适配器）
│   ├── assemble         systemPrompt.assemble 注入 + 冻结快照
│   ├── tools            memory / rules / strategy 工具
│   ├── approval         T1 提案 → ask_user_question
│   └── record           appendPluginRecord 快照
├── memory-mcp/         【预留 v2】只读 MCP 适配器，映射 service
└── memory-ui/          【预留】只读检查器
```

**分层纪律（决定 C 路径成本）**：

1. `memory-core` **不认识 DSH**——不 import 任何 `@deepseek-ai/*`；
2. `memory-dsh` **不认识存储细节**——只调 `MemoryService`；
3. **所有入口行为一致**：CLI/工具/MCP 都只是参数转录，判定全在 core（`agent-memory` 的原话："CLI and MCP must expose the same operation rather than define separate rules"）。

**这条纪律的直接收益**：将来做 C，只需新增 `memory-mcp`（约 200 行映射），核心零改动。

## 五、`MemoryService` 接口（C 路径与付费的接缝）

```ts
interface MemoryService {
  // 读
  recall(q: RecallQuery): Promise<RecallHit[]>;        // 检索（scope/kind/status 过滤）
  read(id: MemoryId): Promise<MemoryBody>;             // 正文
  asOf(q: RecallQuery, date: string): Promise<RecallHit[]>;  // 时间旅行
  rules(): Promise<Rule[]>;                            // 硬约束清单
  stats(): Promise<StoreStats>;                        // 容量、条目数、陈旧项

  // 写（按档位分流）
  record(input: RecordInput): Promise<WriteResult>;    // T0
  correct(id: MemoryId, patch: Patch): Promise<WriteResult>;   // T0（保留旧版）
  supersede(oldId: MemoryId, newId: MemoryId): Promise<WriteResult>; // T0
  propose(input: ProposalInput): Promise<Proposal>;    // T1（不落盘，进 pending）
  decide(id: ProposalId, verdict: 'accept'|'reject'): Promise<void>; // 人工

  // 预留：付费能力（v1 全为 no-op）
  entitlement?: EntitlementHook;
  meter?: MeterHook;
}
```

**关键设计**：`propose` 与 `record` 分开，是 T0/T1 的接口级体现——**模型无法通过任何参数把"删除"变成"直接执行"**。

## 六、C 路径预留：现在做什么、不做什么

**现在做（成本≈0）**：

| 项 | 做法 |
|---|---|
| 服务层抽象 | 上面那个 `MemoryService`，core 内实现，不依赖 DSH |
| scope 字段 | 数据模型里**始终有** `scope`，v1 恒为 `"local"` |
| 只读优先 | `memory-mcp` 只暴露 `recall/read/rules/stats`，**不暴露任何写工具** |
| 行为一致性测试 | 一组"同一操作在不同入口得到同一结果"的测试，v1 先用 CLI + 工具跑 |

**现在不做**：

- 不写 MCP server（等真有第二个客户端需求）；
- 不做鉴权 / token / 多租户隔离；
- 不做 HTTP 服务。

**为什么这么切**：MCP 出口的价值是"让别的客户端读同一份记忆"。而**读**是最容易加、风险最低的。写路径一旦跨客户端，就要面对并发与鉴权，那是 v3 的事。

---

## 七、付费升级预留：只留三个空钩子

你说"暂不做付费，但要留升级可能性"。**关键是不让单用户假设写进数据模型。**

| 钩子 | v1 行为 | 将来可能变成 |
|---|---|---|
| `entitlement.check(feature)` | 恒返回 `allow` | 许可校验（功能开关/席位） |
| `meter.record(op, bytes)` | 只写本地审计 | 用量计量（导出、写入次数） |
| `storage.cap()` | 返回配置里的上限 | 分档配额（免费 1k 条 / 付费无限） |

**三条纪律**：

1. **钩子必须是可选的**——core 在钩子缺失时正常工作，不能有"必须注入"的依赖；
2. **v1 不许有分支逻辑**——不允许写 `if (paid) {...}`，那会污染核心；
3. **数据模型预留但不使用**——`scope` 字段存在即可，不建 `tenant` 表。

**明确调研结论**（你要求"调研相应功能实现的付费升级可能性"）：这条路能自然演化出的付费点是**托管同步与多设备**、**跨客户端并发写**、**审计与合规导出**——都是"存储与协作"层的能力，不是"记忆算法"层。所以**留接口的位置应该在 `MemoryService` 边界，而不是在检索/合并逻辑里**。

## 八、v1 规格（可直接开工）

### 8.1 存储布局

```
<DSH_HOME>/memory/            ← 必须在 agent 沙箱之外（见 06 L0）
├── SOUL.md                   人格（人维护）
├── USER.md                   偏好（条目，§ 分隔）
├── RULES.md                  硬约束（编号，人维护）
├── MEMORY.md                 索引：一行一条（唯一常驻注入）
├── memories/
│   ├── fact/<name>.md        事实正文
│   ├── pitfall/<name>.md     踩坑（按需）
│   └── exp/<name>.md         经历
├── strategy/                 【v2】人工确认的规律
├── archive/
│   ├── sessions/             原始轨迹副本（先落盘再蒸馏）
│   └── provenance/           证据指针
├── audit.db                  追加写审计（含拒绝记录）
└── .state/                   写锁、蒸馏水位
```

### 8.2 单条记忆的 frontmatter

```yaml
---
id: mem-20261017-0007
kind: pitfall                  # fact | exp | pitfall
scope: local                   # v1 恒为 local；预留
abstract: 在 Windows 装 Node 原生模块前先查 Python 与 Build Tools
valid_from: 2026-10-17
invalid_at: null
superseded_by: null
author: agent                  # agent | human
provenance:
  - session: 2026-10-17-node-sqlite
  - seq: 412
weight: 1.0
confidence: 2                  # 1观察 2模式 3规律（由证据算）
---
（正文，自由 markdown）
```

### 8.3 注入契约

| 段 | 来源 | 预算 | 说明 |
|---|---|---|---|
| 人格摘要 | `SOUL.md` 首段（≤200 字） | 200 字 | 全文不进注入 |
| 偏好 | `USER.md` 全文 | ≤1500 字 | 条目式 |
| 硬约束 | `RULES.md` | ≤800 字 | **逐条带编号** |
| 记忆索引 | `MEMORY.md` | ≤1200 字 | 一行一条，≤80 字/行 |
| **合计** | | **≤ 3700 字（约 1200 token）** | 硬上限 |

**规则**：
- 全部放进**不可变区**（protected），压缩不得触及；
- 会话开始时捕获一次，**同一会话内字节稳定**；
- 空文件不注入标题；
- 正文（pitfall/exp 全文）**一律不进常驻**，走 `recall/read`。

### 8.4 三档权限（落到动作）

| 动作 | 档 | 前置条件 |
|---|---|---|
| 新增 fact / exp / pitfall | **T0** | 读前校验、扫描通过、容量允许 |
| 更新（保留旧版） | **T0** | 同上 + `superseded_by` 链 |
| **全等**去重合并 | **T0** | 所有语义字段完全一致 |
| **相似**合并 | **T1** | 提案 → 人确认 |
| 删除（置 `invalid_at`） | **T1** | 提案 → 人确认 |
| 拆分 | **T1** | 提案 |
| 晋升 strategy | **T1** | ≥2 条跨会话证据 + 人确认 |
| 物理清理 | **T2** | 仅人工命令 |
| 改 `RULES.md` / `SOUL.md` | **T2** | **agent 无工具** |

### 8.5 硬约束清单（v1 必须有代码或测试对应）

| 编号 | 约束 | 执行点 |
|---|---|---|
| R1 | 记忆写入只走 `memory` 工具 | 数据目录在沙箱外（物理边界） |
| R2 | 改前必须先读 | 服务端持有"最近读版本" |
| R3 | 写锁在读之前获取，覆盖到投影完成 | core.store |
| R4 | 凭据/不可见 Unicode/注入模式 → 拒绝 | 服务端扫描 |
| R5 | 单文件 ≤10000 字符；`[exp]`+`pitfall` ≤40% | 服务端配额 |
| R6 | 删除只能以提案到达 | `propose` 是唯一删除入口 |
| R7 | 注入段不可被压缩 | protected 区 + 硬拒绝 |
| R8 | 索引可重建不丢知识 | **测试**（`rm -rf index && rebuild` 后逐条比对） |

> R8 就是 `agent-memory` 那句 "enforced by a test, not promised in a doc" 的本地化。

## 十、明确不做（v1 冻结清单）

| 不做 | 理由 |
|---|---|
| 向量检索 | Q1 的规模（几十到一两百条）用 BM25/字面 + scope 足够；留 `Retriever` 接口即可 |
| 自动整合 / 后台复盘 / 技能自提炼 | 论文实测的失效模式（100%→52.6%） |
| 多租户实现、鉴权、计费 | 只留钩子，不写分支 |
| `strategy` 自动生成 | v2 且有门槛 |
| 全量 Web 编辑器 | v1 只读检查器优先 |
| 压缩|摘要作为"记忆" | 压缩管会话内，记忆管跨会话，两件事 |

## 十一、风险与对策

| 风险 | 对策 |
|---|---|
| 分三层导致过度设计 | `memory-core` 允许先做成单包（`src/core|dsh`），**M6 后再拆**；接口边界先立住即可 |
| 索引化注入增加跳数 | v1 从"全注入 + 索引并存"开始，>30 条再启用索引优先 |
| `RULES.md` 与 `USER.md` 边界模糊 | 判定规则：**能不能写出一个会失败的测试？能 → RULES；不能 → USER** |
| 隐私标记被绕过 | `<private>` 剥离在**入库前**，不是"不索引" |
| 付费钩子被滥用成分支逻辑 | CI 检查：`memory-core` 里禁止出现 `entitled|paid|tier` 条件分支 |

## 十二、一句话总结

**v1 = 一个只有几十到几百条记忆的、文件型的、带三档权限和硬约束编号的 DSH 插件；核心与服务分层，让 MCP 将来只是一个适配器；付费只留三个空钩子，一行分支都不写。**

你的四个答案合起来其实说明一件事：**你要的不是"更聪明的记忆"，而是"更可控、更可信、能被审计的记忆"。** 那么 v1 的目标就不是召回率，而是**这几百条里没有一条是错的、没有一条是偷偷写进去的、每一条都能说清来源。**
