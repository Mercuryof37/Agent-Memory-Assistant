## 一、先建立心智模型：记忆不是一个东西，是四个正交的维度

大多数人一上来就问"用哪个记忆框架"，这个问题问错了。原文的拆法是：**先分清你指的是哪一类记忆、以什么方式读、以什么方式写**，框架是这三个答案的乘积，不是起点。

**按载体分四类**，从轻到重：

- **单文件 md 记忆**——最轻，人可读可手改，适合"用户是谁""我们的约定是什么"这类条目化事实；
- **session 历史形成的数据库**——原始日志本身，是最权威、最完整的信息源，只是量大且不结构化；
- **skills 之类的可沉淀经验**——可复用的方法、步骤、踩过的坑；
- **更复杂的 RAG 系统**——语义检索、向量库，适合海量非结构化知识。

**按读取方式分两种**：注入系统提示词（永远在场，零延迟，但吃上下文预算），或作为工具供 agent 按需调用（不占常驻预算，但要模型主动想起来查）。

**按编辑方式分三种**：人工编辑、自动保存、agent 自行调用工具编辑。

**按归属分三类**，这条决定了内容往哪儿写：

| 载体 | 装什么 | 判断标准 |
|---|---|---|
| `USER.md` | 用户明确提供的长期背景、偏好、协作预期 | 是不是"关于这个人"的稳定事实 |
| `MEMORY.md` | 跨任务稳定的事实、背景、长期约定 | 是不是"关于世界和我们的约定" |
| skills | 可复用的方法、步骤、坑和经验 | 是不是"下次还能照做一遍"的流程 |
| 会话／工作文件 | 临时路径、进度、完成日志、TODO、原始资料 | 是不是只在这件事里有意义 |

关键判断句：**"下次开一个新会话，这条信息还有用吗？"** 有 → 进记忆；没有 → 留在会话或工作文件里。原文特别强调"不运行后台学习"——记忆不靠后台慢慢积累，靠对话中实时判断。

## 二、文件怎么设计：散文归散文，事实归事实

原文用 SOUL.md 和 MEMORY.md／USER.md 的对比讲清了一条边界：

- **SOUL.md 是段落式散文**——人格、身份、背景叙事。它描述"我是谁"，可以长、可以有文风。
- **`USER.md` 和 `MEMORY.md` 是条目式事实**——每条极简，用特殊符号隔开。它们描述"我知道什么"，必须精确、可被稳定检索。

这条边界是整个系统能稳住的根。把人格叙事混进事实文件，检索会变得语义模糊；把零散事实写进 SOUL.md，人格会变得支离破碎。

**写入规范（`USER.md` 口径，`MEMORY.md` 同理）**：

- 只写用户明确提供的长期背景、偏好与协作预期，形式是简短事实，必要处附上日期与适用范围；
- 不得编造画像、不得把临时要求升格为永久偏好、不重复实时环境信息、不做后台积累；
- 修改前必须先读最新条目；
- 新增／替换／删除**需经用户确认**；纠正时**优先更新旧条目**，而不是叠加一条矛盾的新条目；
- 替换须提交保留全部有效信息的**完整条目**；
- 格式上：条目以单独一行 `§` 分隔，单条必须非空且完整、内部不得再出现独立 `§` 行；
- **单文件写入上限 10000 字符**。

这几条看着琐碎，实际上每一条都在防一类具体的失败：不读就改 → 覆盖别人的修改；叠加而非更新 → 记忆库里同时存在两条互相矛盾的事实，模型每次都要猜哪个对；替换时只提交增量 → 旧条目被截断成半句话；`§` 出现在条目内部 → 下次读取时条目被切成两条。

## 三、读写记忆：`memory` 工具是唯一入口

有了文件，就要有受控的读写通道。`memory` 工具是读写 `MEMORY.md` 与 `USER.md` 的**专用入口**。

**参数**：`target` 取 `memory` 或 `user`，必填。

**读**：`query` 做字面匹配，返回整条条目；`all: true` 读全文（空 query 不给 all 会报错）；`offset`／`limit` 在命中的条目间分页。

**写**：`add`／`replace`／`remove`；`content` 必须是**完整新条目**，`old_text` 需为完整旧条目或唯一字面子串，**不做语义匹配**。

**三条硬约束**：

1. **改前必须先读过该 target**，否则服务端直接拒绝——这不是刁难，是强制"读—改"顺序，避免盲写覆盖；
2. **版本冲突检测在服务端内部进行，版本号不经过模型**——把并发控制从模型手里拿走，模型就不可能算错版本号；
3. **它是唯一入口，不得用普通文件工具绕过**；它不管 `SOUL.md`（人格文件由人维护）。

**权限设计**：读取免审批，且**只有读操作是并发安全的**。也就是说多个子 agent 可以同时查记忆，但写入必须串行。

## 四、找回说过的话：五个原生历史工具，分三层

记忆文件解决"我记住了什么"，历史工具解决"我们当时到底说了什么"。原文的五个工具分三层用：

**第一层 · 定位会话**

- `session_search`：跨**全部**历史会话搜索，每个会话只返回最强的一条命中——它的用途是**定位**，不是取内容。

**第二层 · 会话内检索**

- `session_event_search`：限定单个会话内搜索；省略 `session_id` 即当前会话。

**第三层 · 展开细节**

- `session_event_read`：按 `seq` 取单条事件的完整原文，可附前后若干条摘要；
- `session_event_trace`：查单条事件的替换链与直接关系；
- `session_trace`：查会话谱系，即完整可见的祖先与后代。

**必须知道的四点**：

- **结果无游标、不分页**——检索要一次问准，别指望翻页；
- **当前会话会排除正在执行调用的那一步**——你查不到自己这次的调用，这是有意为之，避免自指；
- **底层是可重建的 SQLite 索引，覆盖所有工作目录，权威来源仍是原始日志**——索引可以重建，日志不能丢；
- 这套工具解决了**跨 cwd 无法访问**的老问题，也让读取、修改、稳定记忆文件的触发变得可靠。

注意 `session_search` 与 `session_event_search` 的分工：前者**跨会话、每会话一条**，用来"找到是哪次聊的"；后者**单会话内**，用来"那次聊的时候具体在哪一句"。搞反了就会觉得"怎么只能搜出一条"。

## 五、让 agent 会用：MEMORY_GUIDANCE.md 与提示词组装

工具摆在那儿，模型不一定会用。原文的答案是 `MEMORY_GUIDANCE.md`——**被注入进提示词，让 agent 知道如何使用这套记忆系统**。

**它的关键设计是分段注入。** 文件里用 HTML 注释做标记：

```
<!-- personalization-guidance-template:2
这是分段内容源。运行时按开关及主/子 Agent 权限选择片段，不能将全部片段原样注入；标记不发送给模型。
-->
<!-- section:common_intro -->
```

运行时**按开关和主／子 Agent 权限挑选片段**，绝不能把全部片段原样拼进去——否则会出现自相矛盾的指令（比如同时注入"必须问用户"和"无需询问"）。标记本身不发给模型。

**片段矩阵**（以记忆为例）：

| 片段 | 生效时机的行为 |
|---|---|
| `memory_confirm` | 新增／替换／删除前，必须用 `ask_user_question` 说明具体变更并取得同意；即使用户说"记住这个"也一样 |
| `memory_direct` | agent 自主判断并直接用 `memory` 执行，无需提议、提问或等待确认 |
| `memory_readonly` | 子 agent 只能读不能写，修改建议交回主 agent，**不通过普通文件工具绕过** |
| `skills_confirm` / `skills_direct` / `skills_readonly` | 技能管理同理 |

**同意语义写得很严**：一次同意只覆盖该项变更所需的相关调用；**内容或范围实质改变时重新取得同意；拒绝、取消或未回答都不表示同意。**

原文默认选择的是 `memory_confirm` 路线——"用户全程参与记忆内容的管理"。作者明确比较过：这比 hermes 的做法**更精细、更可控**，适合开发者，也适合能力较弱的模型。这是个真实取舍：自动化程度换可控性。

**然后是把文件组装进系统提示词。** DSH 的 preset 机制负责提示词组装和工具组装，原文给出的组装顺序值得抄：

```
【request/header · tools】工具定义（独立字段，不在正文里）
【DSH 固定开场 · order -1000】You are an AI agent powered by DeepSeek Harness.
【SOUL.md】                         人格散文
【MEMORY_GUIDANCE.md】              按开关与权限选段
【DSH 一等公民分段】                 运行时行为规范
【USER.md】                         条目式事实
【MEMORY.md】                       条目式事实（空文件不注入标题）
【user/message · runtime-context】  环境、文件策略、审批策略
【user/message · skill-catalog】
【user/message · time-context】
```

两个细节值得注意：**`order -1000`** 让固定开场排在恒定位置；**空文件不注入标题**——`MEMORY.md` 为空时连标题都不发，不浪费预算也不给模型错误暗示"这里本该有内容"。

## 六、一次完整的记忆生命周期

把上面串起来，实际发生的是这样：

1. 会话开始，preset 把 `SOUL.md` + 选段后的 `MEMORY_GUIDANCE.md` + `USER.md` + `MEMORY.md` 注入系统提示词；
2. 对话中用户说了一句值得长期保留的话；
3. agent 依据 guidance 判断归属（USER？MEMORY？skill？还是留在会话？）；
4. 若是 `memory_confirm` 模式，先用 `ask_user_question` 说明"要新增哪一条、写进哪个文件"并取得同意；
5. 先用 `memory` 读该 target 的最新条目（**没读会被服务端拒绝**）；
6. 用 `add`／`replace`／`remove` 写入完整条目，服务端做版本冲突检测；
7. 之后某个新会话里，agent 不确定背景时先 `session_search` 定位，再 `session_event_search` 缩小，最后 `session_event_read` 展开原文核实；
8. 如果发现记忆与事实冲突，**优先更新旧条目**，而不是新增一条矛盾的。

## 七、踩坑清单

**容量**：单文件上限 10000 字符。写失败时原文的要求是——**说明未保存**，依据当前大小和上限判断该精简、合并还是删除，需要严格减少内容时可在仍超限的情况下逐步保存，再重试原修改。不要默默丢弃。

**状态报告**：工具报错或功能关闭时报告**未保存**，只有工具成功才报告**已保存**。已注入的背景可能落后于磁盘，**工具读取的新事实可立即用于当前任务**——这条解决了"提示词里的记忆是旧的怎么办"。

**子 agent**：只能读，不能写。修改建议交回主 agent。且不得用普通文件工具绕过——绕过等于这套权限设计失效。

**绕过入口**：`memory` 是唯一入口，`read`／`write`／`edit` 不能用来碰 `MEMORY.md`／`USER.md`。

**匹配语义**：`old_text` 是字面匹配，不是语义匹配。想当然用一句"意思差不多"的话去替换，会失败。

**`SOUL.md` 不归 `memory` 管**：人格文件由人维护，agent 不碰。

## 八、上手顺序建议

1. **先建文件，别先建工具**。手写一个 `USER.md`（三五条真实事实）和一个空的 `MEMORY.md`，确认注入生效、确认格式（`§` 分隔、单条完整）。
2. **再开 `memory` 工具，用 `memory_confirm` 模式**。自己当几轮"审批人"，观察 agent 提交的条目质量。这一步的目的是校准它的判断边界——哪些它认为是长期的、哪些其实不是。
3. **然后才放开历史检索工具**。先用 `session_search` 找会话，再用 `session_event_search` 找句子，最后 `session_event_read` 核原文。养成这个三层习惯。
4. **最后按需调 guidance 分段**。等 `confirm` 模式下它的判断稳定了，再考虑切 `direct`；给子 agent 保持 `readonly`。
5. **容量和冲突是长期功课**。定期读全文（`all: true`）做一次整理，合并重复、删除过期、更新矛盾——注意这一步也该走用户确认。

## 附：相关技术路线对比

上文的记忆系统属于"**md 文件 + 专用工具 + 提示词分段注入**"路线。另有一条公开的对比路线可供参考：[yq-nova-agent](https://github.com/YQteam-hq/yq-nova-agent)（单文件 SQLite 记忆层，`remember`/`recall`/`forget` 三个操作，混合检索：向量 + FTS5 + 图），其设计说明见[同团队公开文章](https://dev.to/yqteamdyq/i-built-a-local-memory-layer-for-ai-agents-no-vector-db-one-sqlite-file-27jf)。

两者的取舍方向不同：

| | md 记忆 + 专用工具 | yq-nova 式记忆层 |
|---|---|---|
| 侧重点 | 可控、可读 | 自动化、容量 |
| 存储 | 人能直接打开读写的文件 | 单个 SQLite 文件 |
| 检索 | 关键词匹配 + agent 主动查历史 | 语义检索（向量 + FTS5 + 图） |
| 维护 | 人工确认每次变更 | 自动去重、TTL 过期、后台 GC |
| 代价 | 容量有硬上限 | 需引入 embedding provider 与向量数据 |
