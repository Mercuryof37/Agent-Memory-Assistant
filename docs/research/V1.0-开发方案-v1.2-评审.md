## 0. 总评

v1.2 把"知道要做但没写死"的地方补成了条款，方向对。这一轮**能省的时间不在设计，在冗余**：

1. 持久化机制有 **4 个文件、4 套不变量**（audit / ledger / decisions / txn），其中两个（audit、decisions）各自演化出完整的哈希链与重放规则——对几百条记忆来说，维护成本高于收益；
2. `ProposalInput` 的 5 个变体里有 3 个是**同一件事的写法**（修订、合并、拆分都是"N 个新条目取代 M 个旧条目"）；
3. 配置键**分三批迁移**（S2a 5 个、S3 2 个、S4 2 个），每次都要动 schema + 模板 + 文档 + 门禁；
4. 召回自建 benchmark（200 条记忆 + 40 查询 + per-kind 指标）的**构造时间被严重低估**；
5. S5 作为独立阶段，但它的两个产出分别被 S3（规则渲染）和 S2b（启动校验/封存）提前需要。

结论：**可省约 4–6 人日**，剩余工期从 24.5–32 降到 **约 21–27 人日**；阶段数从 8 个降到 7 个；每阶段验收条目从 6–14 条降到 5–6 条。下面按收益排序。

## 2. 简化清单

### S-1（P0）持久化四件套合一：`audit + ledger + decisions` → 单个 append-only journal

**现状**（v1.2 §3.3、§4.6、§6.2、§6.6）：`audit.jsonl`（可轮转、可关闭、哈希链 `prev`）+ `.state/ledger.jsonl`（不轮转、入账哈希、隔离判据）+ `proposals/decisions.jsonl`（第二真相源、自己的哈希链、`op_id` 幂等、重放顺序）+ `.state/txn/`（意图与恢复）；再叠一个 manifest 的 `ledger_head` tripwire 去查台账被截断。

**问题**：

- 同一条"某记忆已入账/已删除/被采纳"的事实，在 3 个文件里各存一份，`doctor` 要三方对账，任何一方轮转/关闭/截断都触发一类新故障；
- `audit.enabled` 是 S1 已交付的开关，"审计可关"与"篡改检测依赖审计"本来就是对立的，v1.2 用拆出 ledger 解决，代价是多一套机制；
- decisions 的"重放顺序 + 删除不变量 + 与文件冲突时隔离"是三条规则，但它的信息量（谁在何时删了谁）本就是 journal 里的一行。

**建议**：一个文件家族 `.state/journal/0001.jsonl`（满 5 MiB 开下一段，段头写 `prev_head`），每行：

```json
{"seq":123,"at":"...","op":"record|adopt|delete|decide|audit","id":"...","sha256":"...","base_hash":"...","op_id":"...","prev":"<上一行哈希>"}
```

- 启动时读 journal（一次顺序扫）→ 得到 `id → sha256` 台账、删除集、决定集；文件系统是数据真相，journal 是**意图与历史**真相；
- `MEMORY.md` / `.index/manifest.json` 仍是派生物，manifest 只存 `journal_head {seq,hash}`；
- 人读的审计轨迹由 `mem inspect --audit`（或 `mem export --audit`）从 journal 导出，不再是常驻文件；
- 于是删掉：`audit.enabled`、`audit.max_bytes`、独立的 decisions 重放规则、tripwire 的三方对账；`doctor` 的检查变成"journal 链完整 + 文件哈希在台账里 + 删除集一致"。

**收益**：约 **0.75–1 人日**，故障面从 4 个文件降到 1 个文件家族；S2b.4（关 audit、轮转两次）与 §6.6 的 tripwire 验收可直接删掉。
**代价**：`docs/config.md` 里两个 audit 键要标废弃（S1 交付物，需写一条迁移说明）；`mem inspect` 增加一个参数。这是本项目唯一的使用者，现在改比 S6 之后改便宜。

### S-2（P0）提案变体 5 → 2

**现状**（附录 F）：`revise | supersede | merge | split | delete` 五个变体，各自带 `base_hash` / `base_hashes` / `patch` / `parts`。

**问题**：文件不可变（§4.5）之下，"修订"就是"新条目取代旧条目"，与 `supersede` 同构；合并是 N 旧 → 1 新；拆分是 1 旧 → N 新。三者只差基数，却有三套校验（`base_hashes` 对齐、部分提交、`parts` 各自校验），S4.4 / S6.3 都要分别写用例。

**建议**：

```ts
export type ProposalInput =
  | { op: 'supersede'; targets: readonly MemoryId[]; base_hashes: readonly string[]; replacements: readonly RecordInput[]; reason?: string }
  | { op: 'delete';    target: MemoryId; base_hash: string; reason: string };
```

- 1→1 即修订，N→1 即合并，1→N 即拆分；`replacements.length + targets.length` 的组合校验只有一套；
- 语义仍是"采纳后一次性写入，任一失败不部分提交"；
- CLI 可以保留 `mem proposals` 里的友好写法（"修订/合并/拆分"只是展示层）。

**收益**：约 **0.5 人日**，S4.4、S6.3 各少一类边界；`base_hashes` 与新条目的 `valid_from ≥ 旧条目` 校验合并成一处。

### S-3（P0）S5 拆入 S3 与 S2b，阶段 8 → 7

**现状**：S5 只做两件事——解析 `RULES.md` 并校验 `check:/test:/[neg]` 映射；把 `SOUL/USER/RULES` 规范化哈希并入封存。

**问题**：

- S3 的注入必须**逐条渲染带编号与类别的规则**，天然要先有解析器；v1.2 却让 S3 先做注入、S5 再补规则渲染；
- 封存扩展是 `policySchema` 的事，和 `sealed_files` 一样属于"策略与启动校验"，S2b 正在改 `doctor` 与 `startup`；
- 独立成一个 1.5–2 天的阶段，额外付一次 ADR + 主提交 + 阶段门禁的成本。

**建议**：`rules/` 解析与映射校验 → S3（产出改为"召回、注入、规则渲染"）；`sealed_files` + 三文件哈希 → S2b（与 policy v2 迁移同批）。阶段表少一行，S3 估时 +0.5、S2b +0.5，净省约 **0.5 人日**。

### S-4（P0）配置与 policy 一次迁移，并删死键

**现状**：S2a 加 5 键、S3 加 2 键、S4 加 2 键，每次都走"三件套 + docs 门禁"；S1 的 `viewer.enabled/port`、`policy.targets`、`policy.approval.mode` 在 V1 里**没有任何读点**；`distill.max_proposals = 7` 与"硬上限 5"名字不同义；`recall.limit = 8`（上限）与"默认 5 条"语义打架。

**问题**：分三批迁移 = 三轮 schema/模板/文档/测试/门禁往返，还留下"旧键还在、语义已变"的窗口。

**建议**：S2a 第一天做一次**配置冻结**：

| 动作 | 键 |
|---|---|
| 删除 | `viewer.enabled`、`viewer.port`、`policy.targets`、`policy.approval.mode` |
| 收紧/改语义 | `distill.max_proposals` 默认 5、max 5；`recall.limit` 明确为"默认条数"，新增 `recall.max_limit = 20` |
| 新增（一次加全） | `lock.*` 3 个、`limits.*` 2 个、`recall.min_score`、`inject.counter`、`quota.t0_per_session`、`proposals.max_pending` |
| 废弃 | journal 合一后 `audit.*` 两键（S-1） |
| policy | `version: 2`，新增 `sealed_files`（S2b 填充），`scan.private_tag` 枚举改 `reject｜confirm` |

一次改完，`mem policy seal --accept` 一次，`docs/config.md`/`policy.md` 一批更新，`mem doctor` 加"policy 版本 / 待重封"提示。

**收益**：约 **0.5–1 人日**，并消掉"policy v2 到底 S2 还是 S5 升"的悬案（v1.2 目前没写）。

### S-5（P1）召回评估集：200 条 + 40 查询 → 60 条 + 16 查询，门槛后置

**现状**（§6.3、S3.1）：200 条记忆 + ≥40 查询（覆盖 8 类），Recall@5 ≥ 0.80、误返回率 ≤ 10%、p95 < 50 ms、冷启动 < 1 s，且"首次基线后只升不降"。

**问题**：

- 这 200 条记忆与 40 条查询要**手写**（还要覆盖同义、混排、错误码、时间边界、失效、冲突、无答案 8 类），按经验 1–1.5 天；它测的是我们自己造的自建 benchmark，不是用户语料；
- 门槛数字是猜的，首轮很可能不达标，然后出现"为凑指标改分词/补 fixture"的返工——这正是 v1.2 想避免的过拟合，只是换了方向。

**建议**：

- fixture **60 条记忆、16 查询**（12 dev / 4 held-out），保证 8 类各至少 1 条；
- 指标仍全测（Recall@5、误返回、p95、冷启动、常驻内存），但**先测基线、再定门槛**：首轮结果写 ADR-0004，门槛取"基线值向下取整"，之后只升不降；
- 用例名保留 `S3.1`，断言拆成两条：`S3.1a` 指标可测并落盘、`S3.1b` 不低于 ADR 记录的门槛。

**收益**：约 **1–1.5 人日**，且第一个 S3 周就能看到真实数字，不必先攒一周语料。

### S-6（P1）验收条目：67 条 → 每阶段 5–6 条 journey + 一张参数化红队表

**现状**：S2a 11 条、S2b 8 条、S3 12 条、S4 14 条、S5 6 条、S6 9 条、S7 7 条，共 67 条；AGENTS.md 要求"每条对应一个用例名"，实际会催生 67 个 `describe` 和大量共享夹具。

**问题**：验收条目按"机制"切分，测试按"机制"写，端到端路径反而没人守；同类负向用例（S4.2 传 `path`、`session_id`、`target:soul`）本是同一张表的三行。

**建议**：

- 每阶段固定 5–6 条**journey**（用户可见路径），编号不变：S2a 保留 `S2a.1/2/3/8/11` 五条，其余并入对应 journey 的断言；
- 红队类（S4.2/3/5/6/8/9/10）写成**一张参数化表**：`[{name, input, expect}]` 一个测试文件跑完，名字带条目编号；
- 机制级测试（frontmatter 拒绝、有效期边界）保留，但挂在 journey 用例内部，不单独占验收编号。

**收益**：约 **0.5–1 人日** 的测试脚手架；更重要的是"阶段完成"的判断变成"这几条路走得通"，而不是"67 个断言都绿"。

### S-7（P1）快照保留策略简化

**现状**（§6.1）：保留 30 天或最近 50 个，`purge` 可清，`mem inspect` 可见。

**建议**：保留最近 **20** 个文件，捕获新快照时删最旧；无配置键、无时间判断（时间判断在测试里就是时间炸弹）。`purge` 只清该会话的快照。

**收益**：约 **0.25 人日**，少一个配置键与一类时钟依赖。

### S-8（P1）压缩验证：20 次 → 2 次 + 单测

**现状**（S3.6）：压缩 20 次后固定区字节不变。

**问题**：真实会话压缩 20 次要人工造 20 轮长对话，半天起；它证明的是"每轮 section 重渲染后我们的冻结仍生效"，2 次就够，剩下的用"同一 session 多次 assemble 字节一致"（S3.4）覆盖。

**建议**：S3.6 改为"压缩 2 次 + S3.4 单测"；M2 结论出来后按 §6.1 的三种情形之一写 README。

**收益**：约 **0.25 人日**。

## 3. 不能简化、建议反而加一句的

简化不等于松绑。以下保持，且建议在 v1.3 里各自补一句"为什么不能省"：

| 机制 | 为什么保留 |
|---|---|
| 文件不可变 + 台账隔离 | 这是唯一能约束"绕过工具直写"的现实手段（§6.6）；删了，安全表述就只剩口号 |
| `base_hash` + 采纳前重读 | 并发与过期提案的唯一防线，删了就出现"基于旧版本的静默覆盖" |
| 来源绑定（`quote` 子串 + 事件哈希） | 模型伪造来源是主要威胁模型；ADR-0003 已证事件可读 |
| 注入转义 + 预算硬失败 | 结构逃逸与静默截断都是"看起来能用、实际失守"的典型 |
| 工具表快照 + 参数禁字段 | 成本极低（一个测试），拦的是最高频的越权尝试 |
| Windows 持久化口径（不承诺零丢失） | 这是诚实性条款，删了就等于宣称做不到的事 |
| 一阶段一 ADR + 一主提交 | 保留，但 ADR 压到 1 页（见 W3） |

## 4. 开发流程改进

### W1 阶段门禁脚本：`node scripts/stage.mjs S2a`

v1.2 的"阶段完成"= ci 全绿 + smoke + ADR + 涉及 DSH 时 compat。现在是**人肉记四条**。建议一个脚本按序检查并以非零退出阻断：

1. `node scripts/ci.mjs`；
2. `node scripts/smoke.mjs`；
3. `docs/adr/0004-*.md` 存在且含"估时 / 实际 / 回滚"三节；
4. 该阶段验收编号在 `packages/*/test/**` 里各至少出现一次（扫 `S2a.1` 这类字符串）。

**收益**：把"完成"从口头约定变成可执行检查，且免掉每次手工核对。

### W2 smoke 当可执行规格：每阶段先加一条失败的 journey

S2a.8（add → read → recall → rebuild 后仍命中）已经是这个模式，建议写成规则：**每个阶段的第一笔提交 = 往 `scripts/smoke.mjs` 加一条新 journey（此时必然失败）；最后一笔提交 = 它变绿**。这样 smoke 从"成功路径冒烟"升级为"阶段说明书"，也自动覆盖 S-6 的 journey 要求。

### W3 ADR 压到 1 页，加"估 / 实"两列

现在 ADR-0003 已 10 KB。模板固定五节：问题、选择、被否方案、证据（链接）、偏差与回滚；另加一张两行表记录**计划工期 / 实际工期**。估时偏差从"靠感觉"变成"有数据"，W1 的第 3 步顺带校验。

### W4 单一 `docs/plan/open-questions.md`，方案在阶段内冻结

v1.1 → v1.2 是一次全文重写（45 KB → 33 KB），下一轮如果每发现一个问题就重写全文，维护成本会吃掉开发时间。建议：每阶段开工前把未决问题列进 `open-questions.md`（每条带"最晚解决阶段"），阶段门禁时清零或带标记延续；方案正文只在阶段边界改一次。

### W5 方案文档分层，完成阶段折叠

v1.3 目标 < 300 行：S0、S1 压缩成各 5 行 + ADR 链接；S2a 起保留完整验收。历史细节留在 ADR 与 `docs/research/`，方案本身只描述"还没做的事"。这条也顺带解决 §1 的引用错位。

### W6 评审节奏：阶段边界一次，不逐版重写

本轮（以及上一轮）的评审都发生在同一阶段内。建议把"方案评审"固定为**每阶段结束时**的一次动作（输入：ADR + 实际偏差 + open-questions），避免同一份文档被反复全文审读。
