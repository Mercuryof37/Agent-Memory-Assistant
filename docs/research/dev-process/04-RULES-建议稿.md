# RULES 建议稿（基于大厂与 AI 公司开发流程调研）

> 这份文档是**建议**，不是规则本身。RULES 只能由人在「偏好与规则」界面保存并封存；agent 不写、不封存。
> 依据：`packages/core/src/rules/rules.ts` 的校验规则——`[机器门禁]` 必须带 `check:`（文件里真实存在的符号）、`test:`（真实存在的测试文件，且含至少一个 `[neg]` 用例）；`[模型指引]` 不得出现"保证/guarantee"；编号不复用。
> 现状：`RULES.md` 已有 1–3 条，本稿从第 4 条起编号。

## 1. 阶段 A：可直接追加（已满足校验条件）

以下 7 条可以直接粘贴到 `RULES.md` 末尾，再由人保存、封存。其中第 4 条是唯一需要 `check/test` 的机器门禁，它引用的符号与 `[neg]` 用例都已存在。

```markdown
4. [机器门禁] 每条 [机器门禁] 必须给出 check 与 test，且 test 文件至少包含一个 [neg] 用例。
   check: packages/core/src/rules/rules.ts#validateRules
   test: packages/core/test/rules/rules.test.ts

5. [模型指引] 涉及数据格式、召回/注入算法、提案与权限语义的变更，先写 ADR 再写代码；ADR 必须写清兼容与回滚。
6. [模型指引] 一个提交只做一件事，行为变更与重构分开；同一提交必须带对应测试。
7. [模型指引] 修复缺陷必须附"修复前失败、修复后通过"的测试；同一逻辑存在多份实现时，一起检查。
8. [模型指引] 提交 agent 产出的改动前，先把 diff 压到最小，附复现步骤与相关测试结果，不提交临时脚本或样例文件。
9. [模型指引] 删除或改变数据格式、公开 API、MCP 工具签名，必须给出弃用期与迁移说明；补丁版本不删除功能。
10. [模型指引] 规则与偏好只由人在界面保存并封存；模型只能提案，不得保存、封存或批准例外。
```

逐条理由：

| 条目 | 为什么加 | 来源 |
|---|---|---|
| 4 | 防止"伪门禁"（写了 `[机器门禁]` 却没有真实检测），让规则自我约束 | 本仓库 validator；OpenAI 的"人类批准预算增加" |
| 5 | 数据/算法/权限变更一旦出错不可逆，必须留下设计与回滚依据 | PEP 1、Rust RFC、K8s KEP |
| 6 | 大提交混改动导致无法定位与回滚 | Google Small CLs、K8s PR 指南 |
| 7 | 只测 happy path 会让"修复"无法证明 | Anthropic `REVIEW.md` 的"先失败后通过" |
| 8 | agent 生成物常见问题是 diff 过大、夹带临时文件、缺复现 | Hugging Face `CONTRIBUTING.md` |
| 9 | 字段/接口/工具删除会直接打断用户既有数据与调用 | vLLM 弃用流水线、Anthropic breaking-change 政策 |
| 10 | 规则与偏好是"人的决定权"，不能被 agent 代劳 | 本仓库架构硬约束；OpenAI `AGENTS.md` |

注意：第 4 条是"规则约束规则"，文案里出现 `[机器门禁]` 字样不会影响解析（解析只看行首编号与分类）。

## 2. 阶段 B：先补测试，再升级为机器门禁

以下 4 条建议目标明确，但**当前没有对应测试文件含 `[neg]` 用例**，现在写成 `[机器门禁]` 会被校验器拒绝。正确顺序是：先补测试并让 CI 通过，再改条目分类。

### B1 记忆写入只经统一入口

- 建议文本：所有记忆写入必须经过 store 的校验、锁与 journal，不得直接写 `memories/` 文件。
- `check: packages/core/src/store/store.ts#MemoryStore`
- 需新增测试：`packages/core/test/store/write-path.test.ts`，含 `[neg]`——绕过 store 的直写不被索引识别或明确被拒绝。
- 价值：防止 GUI/MCP/CLI 各自复制写入逻辑（这是架构硬约束，但缺一条"可检测"的规则）。

### B2 提案决定必须校验 base_hash

- 建议文本：采纳提案前必须校验 `base_hash`，过期则拒绝并保留待审文件。
- `check: packages/core/src/proposals/proposals.ts#decideProposal`
- 需新增 `[neg]`：先改记录再采纳，期望被拒绝且提案仍在 `pending/`。
- 价值：防止"基于旧内容"的重放覆盖。

### B3 规则与偏好只来自人工保存路径

- 建议文本：RULES/USER 的写入只能来自人操作的 GUI 保存路径，模型工具、HTTP、MCP 均不可写。
- `check: packages/dsh/src/gui.ts#/api/agent-memory/rules`
- 需新增 `[neg]`：以模型工具/HTTP 身份调用写入，期望被拒绝且文件未变。
- 价值：把"人保留决定权"从口号变成测试。

### B4 注入失败只降级可选段

- 建议文本：注入组装失败时只降级出错的段，必需段（存储完整性/封存）仍然全局失败。
- `check: packages/core/src/inject/assemble.ts#assemble`
- 需新增 `[neg]`：USER 段损坏时，RULES 与 MEMORY 段仍注入，且 health 记录该段失败。
- 价值：避免"一个文档坏了，整个记忆功能消失"。

> 提醒：B1–B4 的 `check:` 符号目前存在，但 `test:` 指向的文件需要先创建；在测试补齐前，先把它们写成 `[模型指引]` 或暂不写入，否则保存会失败。

## 3. 阶段 C：不建议写入 RULES 的内容

- **代码风格与命名**：交给 formatter/lint；写进规则只会占注入预算，且无法穷举。
- **一次性事故的处理办法**：写 pitfall 记忆，供召回时参考；不要升级成永久规则。
- **空泛要求**（"要写测试""要注意质量"）：无法检测，且会让规则体系失去可信度。
- **依赖特定版本的临时绕行**：过期后误导；放 ADR/issue，附失效条件。
- **与现有条目重复或冲突的**：先合并，再新增；规则数量宁少勿多。
- **需要具体数值但无法维护的**（如"图不超过 200 节点"）：放配置或代码常量，不写规则。

## 4. 规则的预算与准入

- `inject.rules_max_chars` 默认 **1200**，`inject.total_max_chars` 默认 **4000**（`docs/config.md`）。新增规则前先估算字节数，超预算应合并或降级。
- 建议准入三问：
  1. **来源**：是重复犯错、评审结论还是事故复盘？（写不出就说明还不该成规则）
  2. **反例**：有没有一个真实场景说明不加会出错？
  3. **检测**：能否用 `check/test/[neg]`？不能就只做 `[模型指引]`。
- 建议退役三问：
  1. 已被代码/测试固化，规则是否冗余？
  2. 是否与其他条目冲突？
  3. 是否长期无人违反、也没有反例？（可降级为记忆或 `[废止]`）

## 5. 落地步骤

1. 人审阶段 A 的 7 条：确认与现有 1–3 条不冲突。
2. 在 GUI 保存并封存；确认注入字节数在预算内（`doctor`/注入预览可见）。
3. 阶段 B 逐条处理：先补 `[neg]` 测试 → `node scripts/ci.mjs` 通过 → 把条目改成 `[机器门禁]` → 保存封存。
4. 每季度审视一次：合并、降级、标 `[废止]`；保留编号，不重用。

## 6. 预期效果与风险

- 效果：把"流程要求"从口头约定变成可检测条目；把人的决定权写成可审计的边界；减少 agent 生成改动的返工。
- 风险：规则过多会挤占注入预算、互相冲突；因此本稿刻意只给 7 条，且其中只有 1 条是机器门禁。
- 不做的事：不新增"不可检测的门禁"；不把产品承诺写成规则；不自动保存、不自动封存。
