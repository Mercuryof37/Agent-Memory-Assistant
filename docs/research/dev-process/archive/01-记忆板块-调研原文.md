# 记忆板块：开发流程借鉴（大厂与 AI 公司开源实践）

> 范围：本板块对应「记忆」侧栏工作台与背后的记录层——事实/坑/经验三类记录、提案与决定、召回（BM25/混合）、注入快照、导出导入。
> 目标：把外部团队在**数据正确性、证据、兼容、回滚**上的流程做法，落成本板块可执行的门禁与检查单。
> 本文只借鉴流程，不复制产品功能。

## 1. 外部流程要点

### 1.1 先设计，再实现：把"改数据格式"当 RFC 级变更

- Python 的 PEP 把变更分成 Standards Track / Informational / Process 三类，明确"PEP 是设计文档 + 理由 + 决策记录"，修订历史本身就是历史档案（[PEP 1](https://github.com/python/peps/blob/main/peps/pep-0001.rst)）。
- Rust 的 RFC 流程规定：语义/语法变更、删除特性、标准库大改都要先走 RFC；进入 FCP 前子团队必须全部签核，FCP 持续 10 天；RFC 在 PR 上可见后**禁止 squash/rebase**，保证讨论可追溯（[Rust RFC README](https://github.com/rust-lang/rfcs/blob/master/README.md)）。
- Kubernetes 的 KEP 明确"非平凡变更默认需要提案"，理由是留下**结构化的历史记录**与**明确的 approver/reviewer**（[KEP README](https://github.com/kubernetes/enhancements/blob/master/keps/README.md)）。
- 对本板块的直接含义：`mem_schema`、字段语义、提案类型、召回/注入算法、证据规则，都属于"先 ADR/RFC、后代码"的范畴；纯文案与样式不需要。

### 1.2 小步提交：一个变更只做一件事，测试同批

- Google 的 Small CLs：合适大小是"一个自包含的变更"，约 100 行合适、1000 行通常过大；必须带上相关测试；大变更在被否时浪费更多，回滚也更难（[small-cls](https://github.com/google/eng-practices/blob/master/review/developer/small-cls.md)）。
- Kubernetes 的 PR 指南同样要求小而聚焦的 PR，并建议"修复与通用功能分开开 PR"（[pull-requests](https://github.com/kubernetes/community/blob/master/contributors/guide/pull-requests.md)）。
- 对本板块的含义：schema 变更、索引重建、注入段调整、UI 对齐不要混在一个提交里；否则出问题时无法只回滚一半。

### 1.3 评审先看设计与复杂度，测试是门槛而非装饰

- Google 的评审清单顺序是：设计 → 功能 → 复杂度/过度设计 → 测试 → 命名/注释/风格；特别提醒警惕 over-engineering（[looking-for](https://github.com/google/eng-practices/blob/master/review/reviewer/looking-for.md)）。
- 评审速度上，Google 要求**一个工作日内首次响应**，因为"响应慢"比"要求严"更伤团队（[speed](https://github.com/google/eng-practices/blob/master/review/reviewer/speed.md)）。
- Microsoft 的工程手册直言："代码没有测试就是不完整的"，单测在合并前必须跑，测试要早写（[automated-testing](https://github.com/microsoft/code-with-engineering-playbook/blob/main/docs/automated-testing/README.md)）。
- 评审目标被 Microsoft 定义为三件事：提高质量、互相学习、形成对代码的共同理解（[code-reviews](https://github.com/microsoft/code-with-engineering-playbook/blob/main/docs/code-reviews/README.md)）。

### 1.4 负向用例与"先失败后通过"是硬要求

- Anthropic 的 SDK 仓库把评审要求写成 `REVIEW.md`，其中直接点名：**一个修复如果没有"修复前失败、修复后通过"的测试，要按 Important 报**；同一逻辑存在多份副本时，只改一份也要报（[REVIEW.md](https://github.com/anthropics/anthropic-sdk-python/blob/main/REVIEW.md)）。
- 它的 `CLAUDE.md` 还把测试矩阵、warnings-as-errors、生成代码与手写代码的边界写清楚，避免"改错层"（[CLAUDE.md](https://github.com/anthropics/anthropic-sdk-python/blob/main/CLAUDE.md)）。
- 对本板块的含义：拒绝路径（坏 frontmatter、坏证据、坏关系、越权写入）必须有 `[neg]` 用例；只测"能存能读"不够。

### 1.5 证据与可复现：先复现，再最小 diff

- Hugging Face 在 `CONTRIBUTING.md` 里专门写了"agent 时代的贡献"：要求**先复现问题**、**把 diff 压到最小**、**对照同类实现**、**本地与 CI 测试通过后再请人评审**（[transformers CONTRIBUTING](https://github.com/huggingface/transformers/blob/main/CONTRIBUTING.md)）。
- OpenAI 的 SDK 要求非协作者只提 issue，issue 必须包含版本、期望/实际行为、最小且脱敏的复现；依赖更新有 8 天冷却期（[CONTRIBUTING](https://github.com/openai/openai-python/blob/main/CONTRIBUTING.md)）。
- 对本板块的含义：记忆写入的证据（`event_seq` + `quote`）与提案的 `base_hash` 就是"可复现"；修数据问题时先写复现脚本与失败用例，再改实现。

### 1.6 兼容与弃用要有流水线，不在补丁里删东西

- vLLM 的弃用策略把生命周期分成"仍然默认开启 → 默认关闭但可恢复 → 移除"三段，跨多个 minor（Y）版本；每个阶段都要在 help、日志、文档、release notes 中提示；**禁止在 patch 版本里移除功能**（[deprecation_policy](https://github.com/vllm-project/vllm/blob/main/docs/contributing/deprecation_policy.md)）。
- Anthropic 的仓库把"破坏性变更"定义成运行时行为而不是签名，要求保留别名、等待弃用周期，并用脚本对比基线检测公开符号删除（[CLAUDE.md](https://github.com/anthropics/anthropic-sdk-python/blob/main/CLAUDE.md)）。
- 对本板块的含义：字段/工具/命令/API 的删除要走同样的三段式；旧 `mem_schema: 1` 记录继续可读，不做静默重写。

### 1.7 事后评审与回滚是常态，不是失败

- LLVM 的政策明确鼓励 post-commit review；如果社区成员对已提交改动有重大疑问，可以要求作者**及时回滚**，让设计讨论不阻塞其他人，之后可以原样再提交（[CodeReview](https://github.com/llvm/llvm-project/blob/main/llvm/docs/CodeReview.md)）。
- 对本板块的含义：mem 的记录/索引变更出问题时，优先 `revert` 到上一个可用版本，再在 issue/ADR 里讨论；不要"在主干上边跑边修"。

### 1.8 AI 参与的边界要写死

- OpenAI 的 `AGENTS.md` 规定：agent 不得批准预算增加、不得绕过门禁；安全要求（密钥、日志脱敏、依赖审查、Actions 固定 SHA）是给编码 agent 的硬约束（[AGENTS.md](https://github.com/openai/openai-python/blob/main/AGENTS.md)）。
- Hugging Face 明确：首贡献者不要用 code agent 提 issue/PR，agent 除非人类确认价值，否则会被直接关闭（[CONTRIBUTING](https://github.com/huggingface/transformers/blob/main/CONTRIBUTING.md)）。
- 对本板块的含义：模型在记忆板块只能"检索 + 提案"，不能决定、不能写 RULES；这条已有代码门禁，流程上再补一条"agent 产出必须附证据与测试"。

## 2. 对本板块的启示（现状 → 该补的流程）

| 现状 | 流程缺口 | 借鉴 |
|---|---|---|
| `store.add`/`addMany` 有校验、锁、journal、内容去重 | 没有把"什么级别的变更必须先写 ADR"写成清单 | PEP/RFC/KEP |
| 提案有 `base_hash` 校验 | 缺少"过期提案"的固定复现用例 | Anthropic 的"先失败后通过" |
| 有 `[neg]` 用例，但数量少 | 数据格式/关系/权限的拒绝路径覆盖不全 | Microsoft 测试门槛 |
| 有 `docs/eval` 基线 | 召回/注入改动没有规定必须跑基线对比 | HF 的"本地验证 + CI" |
| 有 `mem_schema` 版本读法 | 弃用没有三段式时间表 | vLLM 弃用流水线 |
| 有 revert 能力 | 没有写"何时必须 revert" | LLVM |
| 模型只能提案 | 没有规定 agent 产出的评审材料 | OpenAI/HF |

## 3. 建议流程（六步，产物明确）

1. **分级**：把变更分成 A（数据格式/证据规则/召回与注入算法/提案与权限）、B（接口与命令）、C（UI/文案）。
   - A 类：先写 ADR（写清动机、替代方案、兼容与回滚），再动代码；跨模块的 A 类再补一份 RFC 式设计（对齐 PEP/KEP 的"结构化记录"）。
   - B 类：在 ADR 或 PR 描述里写契约变化与迁移；C 类：小 PR 直接做。
2. **设计稿**：字段、旧记录如何读、失败姿态（响亮失败 or 降级）、回滚方式、验收用例清单。缺任意一项不进入实现。
3. **实现**：小步提交；同一个 PR 带正向与 `[neg]` 测试；测试数据只进临时目录（仓库既有约定）。
4. **评审**：按"设计 → 功能 → 复杂度 → 测试 → 风格"的顺序看；A 类变更必须有人指出"回滚路径是什么"；A 类 PR 不允许混入 UI 改动。
5. **验证**：`node scripts/ci.mjs`；A 类变更额外跑 `docs/eval` 基线对比与一次真实会话的 import/export/rebuild 冒烟。
6. **发布与回滚**：release note 写迁移与弃用；出问题先 revert；弃用按三段式走，补丁版本不删功能。

## 4. 门禁与验收（可直接转成测试/检查单）

- [ ] A 类变更的 ADR 存在，且含"兼容/回滚"两节（可用脚本检查 ADR 标题）。
- [ ] 每个修复都有失败复现用例 + 通过用例（同一测试文件）。
- [ ] 每个拒绝路径至少一个 `[neg]` 用例（坏 frontmatter、坏证据、坏关系、越权来源）。
- [ ] 提案 `base_hash` 过期时被拒绝且待审文件保留。
- [ ] 旧 `mem_schema: 1` 记录在新版本下仍可读，且不被静默重写。
- [ ] 召回/注入改动附基线对比结果（命中率/延迟/字节数）。
- [ ] 删除字段/工具/命令时，release note 含 removals 与替代路径。
- [ ] revert 演练：任取上一个发布版本，能按文档回滚并跑通 smoke。

## 5. 反模式（来自外部实践的警告）

- 大 PR 混重构与行为变更（Google/K8s）。
- 只测 happy path，不测拒绝路径（Anthropic 的评审清单）。
- 以"兼容"为名无限期保留旧字段，却没有弃用时间表（vLLM 的反面）。
- 用 agent 生成大量"看起来正确"的改动，但没有复现与最小 diff（HF 明确反对）。
- 事后评审变成"只提意见不修"，没有 revert 兜底（LLVM 强调及时回滚）。
