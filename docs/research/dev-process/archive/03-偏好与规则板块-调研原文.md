# 偏好与规则板块：开发流程借鉴（大厂与 AI 公司开源实践）

> 范围：本板块对应「偏好与规则」与背后的 `SOUL.md` / `USER.md` / `RULES.md` / 注入时的 `GUIDANCE`：偏好条目、规则条目、封存（seal）、规则注入预算，以及"规则只能由人保存"的审批边界。
> 目标：把外部团队在**策略即代码、人工批准点、规则评审与退役、AI 参与边界**上的流程做法，落成本板块的门禁与检查单。

## 1. 外部流程要点

### 1.1 约束要"可执行"，不是写在文档里靠自觉

- 本仓库的 RULES 已经区分 `[机器门禁]` / `[模型指引]` / `[废止]`：机器门禁必须给出 `check:`（存在的符号）、`test:`（存在的测试文件）且测试文件里至少一个 `[neg]` 用例，否则 `validateRules` 拒绝保存（`packages/core/src/rules/rules.ts`，测试 `packages/core/test/rules/rules.test.ts`）。
- Google 的评审标准强调"代码健康随每次变更改善"，而不是靠口头约定（[The Standard of Code Review](https://github.com/google/eng-practices/blob/master/review/reviewer/standard.md)）；规则同理：能进 CI 的才写成门禁，进不了 CI 的只能当指引。
- OpenAI 的仓库把"自定义代码预算"做成 ratchet 指标，并且**预算增加必须由人类审批**，agent 不得批准、不得绕过（[AGENTS.md](https://github.com/openai/openai-python/blob/main/AGENTS.md)）。这是"硬约束 + 人批准"的典型组合。

### 1.2 人工批准点要指名道姓

- Kubernetes 用 `OWNERS` 文件声明每个目录的 approver/reviewer，合并需要批准（[owners](https://github.com/kubernetes/community/blob/master/contributors/guide/owners.md)）。
- OpenAI 用 CODEOWNERS + "human approving review" 守住预算与安全变更（[AGENTS.md](https://github.com/openai/openai-python/blob/main/AGENTS.md)）。
- 本仓库的对应物是：RULES 只能由人在 GUI 保存并封存；模型只能提案。流程上应把"谁批准、批准什么、批准后如何审计"写清楚，而不是只靠产品文案。

### 1.3 规则评审要引用规则原文

- Anthropic 的 `REVIEW.md` 要求评审者发现违规时**引用 `CLAUDE.md` 里的具体条目**，并把"PR 描述未列出的新公开名称""特性关闭后仍改变行为""没有先失败后通过测试的修复"列为必须报告的问题（[REVIEW.md](https://github.com/anthropics/anthropic-sdk-python/blob/main/REVIEW.md)）。
- 这给规则评审一个可操作的格式：指出**违反了哪条**、**证据是什么**、**影响是什么**；而不是"感觉不太对"。

### 1.4 规则也要退役，不能只增不减

- vLLM 的弃用策略要求：先标记并给出移除版本 → 默认关闭但可恢复 → 移除；跨多个 minor，禁止在 patch 中删除（[deprecation_policy](https://github.com/vllm-project/vllm/blob/main/docs/contributing/deprecation_policy.md)）。
- 本仓库的对应物是 `[废止]` 标签：编号保留、条目保留、默认不注入。流程上应规定"什么情况退役、谁决定、如何留痕"。

### 1.5 规则会挤占注入预算，必须像资源一样管理

- 本仓库注入按段与预算组装（SOUL 100 / GUIDANCE 110 / RULES 150 / USER 200 / MEMORY 300），`GUIDANCE` 随模式（confirm/direct/readonly）变化且有字符预算（`docs/architecture/overview.md` §5.1）。
- 规则越多，注入越贵、冲突越多。流程上应有"规则预算"：新增一条前先问能否合并、能否降级为 pitfall/记忆。

### 1.6 AI 参与边界要写进流程

- Hugging Face 直接限制首贡献者与自治 agent 提 PR，理由是维护者被 agent 生成的 PR 淹没（[CONTRIBUTING](https://github.com/huggingface/transformers/blob/main/CONTRIBUTING.md)）。
- OpenAI 为编码 agent 写了安全要求（密钥、日志脱敏、依赖与 Actions 审查），并禁止 agent 批准预算（[AGENTS.md](https://github.com/openai/openai-python/blob/main/AGENTS.md)）。
- 对本板块的含义：agent 可以建议规则、可以指出规则冲突，但不能保存规则、不能封存、不能批准例外；这条在代码里是硬约束，在流程文档里也要重复。

## 2. 对本板块的启示（现状 → 该补的流程）

| 现状 | 流程缺口 | 借鉴 |
|---|---|---|
| RULES 有机器门禁三件套 | 缺少"新增规则前的必要性评估" | Google 标准 / 规则预算 |
| RULES 只能人保存、可封存 | 批准人与审计说明不够显式 | OpenAI human approving review / K8s OWNERS |
| 有 `[废止]` 机制 | 没有退役触发条件与时间表 | vLLM 弃用流水线 |
| 有 GUIDANCE 模式与预算 | 没有"规则数量/字节"上限的评审 | 注入预算 |
| 模型只能提案 | agent 产出的规则建议缺少评审格式 | Anthropic 引用规则原文 |
| 有 USER 偏好 | 偏好与规则的边界没有写成检查项 | 分类原则 |

## 3. 建议流程（五步）

1. **提出**：规则建议必须写清来源（重复犯错的会话/评审结论/事故）、适用面、反例；来自 agent 的建议必须标注"未经人确认"。
2. **分类**：先判断能否检测——
   - 能检测：写成 `[机器门禁]`，同时提交 `check:` 引用、`test:` 文件与 `[neg]` 用例；三件缺一不保存。
   - 不能检测但不写会反复出错：写成 `[模型指引]`，措辞不得出现"保证/guarantee"（校验器会拒绝）。
   - 一次性教训：写记忆（pitfall），不写规则。
3. **评审**：检查与其他条目的冲突、重复、是否挤占预算；评审意见引用规则原文（Anthropic 式）。
4. **批准与封存**：只能由人在 GUI 保存并封存；保存后注入快照才会更新；记录谁、何时、为什么（journal/ADR）。
5. **退役**：合并、降级或标 `[废止]`；编号保留，不重用；若涉及系统行为变化，按弃用三段式给迁移期。

## 4. 门禁与验收（可直接转成测试/检查单）

- [ ] 每条 `[机器门禁]` 都有 `check:`（真实符号）与 `test:`（真实文件且含 `[neg]`），否则保存失败。
- [ ] `[模型指引]` 不出现"保证/guarantee"字样。
- [ ] 规则编号不重复；退役条目保留编号并标 `[废止]`。
- [ ] RULES 只能经人工保存路径写入；模型工具/HTTP/MCP 均不可写（负向用例）。
- [ ] 封存后注入使用新文本；未封存不生效。
- [ ] 规则新增前后，注入字节数在预算内；超预算时失败或降级可解释。
- [ ] 每条新规则能回答三个问题：来源、反例、怎么检测（或为什么不能检测）。

## 5. 反模式

- 把"要写测试""要小心"这类空泛要求写成规则（不可检测，只会占预算）。
- 一次事故写一条规则，半年后规则互相矛盾。
- 用 `[模型指引]` 冒充 `[机器门禁]`（校验器会拦住，但流程上也不该尝试）。
- agent 自动"保存规则"或"封存规则"。
- 规则改了但不封存，以为已生效。
- 退役靠删除文本（应保留编号与 `[废止]`）。
