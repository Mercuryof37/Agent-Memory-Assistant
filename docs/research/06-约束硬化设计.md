# 06 · 约束硬化设计：从"宪法"到"门禁"

> **触发**：用户指出 —— `AGENTS.md` 之类的约束若只停留在 prompt 里，是 agent 可自行选择绕过的软约束，必须做成系统设定。
> **结论先行**：`AGENTS.md` 天生不可能自我生效。它是一份**文档**，而文档只能影响"模型愿不愿意遵守"，不能决定"系统允不允许发生"。本文把这套约束拆成三层：**能硬化的下沉到代码/沙箱；不能硬化的改用"效果校验"；剩下真正只能软化的，明确标注并停止依赖。**
> **环境**：DSH `0.2.0-rc.2` / 文件策略 `workspace-write` / 审批策略当前为 `ask`

---

## 一、问题的本质：文档 vs 门禁

先把两种东西分清楚：

| | 文档（宪法式） | 门禁（系统式） |
|---|---|---|
| 载体 | `AGENTS.md`、`MEMORY_GUIDANCE.md`、系统提示词 | 代码分支、服务端校验、沙箱、文件权限、测试 |
| 生效方式 | 模型读完**选择**遵守 | 不满足条件**根本发生不了** |
| 失效条件 | 模型忽略、上下文被压缩掉、被注入文本覆盖、换成更弱的模型 | 只有改代码才能绕过 |
| 可验证性 | 不可验证（无法证明它遵守了） | 可验证（跑攻击测试，必须失败） |

**那句最关键的话**，是 OpenClaw 官方文档自己写的：

> *"Memory can preserve approval context, but **it does not enforce policy**. Use approval settings, sandboxing, and scheduled tasks for hard operational controls."*
>
> 记忆可以保留「批准上下文」，但**它不执行策略**。

而 Amadeus 的文档也坦白过同一件事：

> "「允许管理个人 Skills」和「Skills 变更需确认」**只通过 MEMORY_GUIDANCE 约束 Agent 行为，不是文件权限**。"

**这两位作者都非常清楚这是软约束。** 所以问题不是"他们写错了"，而是"我们不该把它当硬保证用"。

---

## 二、约束分级：哪些能硬化，哪些不能

先把所有约束分三类，否则会陷入"什么都想硬化"的泥潭。

### A 类 · 可硬化（必须硬化）

这类约束的**判定标准客观、执行点明确**，完全可以做成"不满足就发生不了"：

| 约束 | 硬化手段 |
|---|---|
| 记忆文件只能通过 `memory` 工具改，不能被 `write`/`edit`/`bash` 直接改 | **文件放在 agent 沙箱之外**（物理边界，见第三节） |
| 单文件 ≤ 10000 字符 | 服务端写入前校验，超限拒绝 |
| 条目以 `§` 分隔、单条非空、条目内不得含独立 `§` 行 | 解析器校验，失败拒绝 |
| 改前必须先读 | 服务端持有"本会话最近读到的版本"，未读即拒 |
| 版本冲突检测 | 服务端 CAS，版本号**不交给模型** |
| 写入需用户确认 | 审批门放在**服务内部**，且在无应答者时**失败关闭** |
| 子 agent 只能读不能写 | 服务端按调用者身份判定，不靠提示词 |
| 不写敏感凭据 | 服务端扫描（凭据特征/不可见 Unicode/注入模式） |
| `SOUL.md` 不被 `memory` 工具修改 | 工具参数里**没有** `target: soul` 这个枚举值 |
| 策略文件不被 agent 改 | 策略文件在沙箱外 + 启动时校验哈希 |

### B 类 · 只能"用效果校验"替代

这类约束是**行为性**的，但你真正在乎的是**结果**，所以可以校验结果：

| 约束（行为表述） | 真正在乎的结果 | 硬化落点 |
|---|---|---|
| "不要自动整合记忆" | 库里没有未经人工触发的合并/改写记录 | 审计表里标记 `origin: auto|manual`，自动整合记录数必须为 0（测试断言） |
| "不把临时要求升格为永久偏好" | `USER.md` 里没有短半衰期条目 | 写入时强制 `ttl` 或 `expires_at`；无 TTL 的条目需显式 `permanent: true` |
| "提示词注入内容不得进入记忆" | 库中无注入模式命中 | 写入前扫描；命中即拒（见 A 类） |
| "回答用中文" | ❌ 无法从结果判定 | 归入 C 类 |
| "不要过度设计" | ❌ 无法从结果判定 | 归入 C 类 |

### C 类 · 真的只能软化（必须标注，不许假装）

这些**只能**靠提示词，且必须**在文档里写明"这是软约束"**：

- 语言与语气、解释详略；
- 何时觉得某条信息"值得记"（价值判断）；
- 代码风格、"不随意引入新依赖"；
- "不过度设计"、"优先复用官方能力"。

**处理原则**：C 类保留在 `AGENTS.md` 里，但**每一条都要标注 `[软]`**，并且不允许用它来担保安全性、正确性或合规性。

## 三、五层纵深防御（DSH 落点）

从最硬到最软排列。**每一层都假定上一层已被突破**。

### L0 · 物理边界：把文件放到 agent 够不到的地方

这是**唯一真正不可绕过的一层**。

DSH 的文件沙箱按策略约束**工具的文件操作**：当前 `workspace-write` 只允许改会话工作区（本会话是 `D:\Deepseek`）。**工作区之外的路径，agent 的 `write`/`edit`/`bash` 都够不到**（需要审批，或直接被拒）。

而插件是跑在宿主进程里的，**不受这个沙箱约束**。

**所以正确布局是**：

```
agent 沙箱内（可被 write/edit/bash 触及）        agent 沙箱外（只有插件/repl 能触及）
────────────────────────────────────         ────────────────────────────────────
<workspace>/PLAN.md                            <DSH_HOME>/memory/
<workspace>/AGENT_HANDOFF.md                     ├── USER.md
<workspace>/.amadeus/skills/*                    ├── MEMORY.md
                                                 ├── SOUL.md          ← 人不经 agent 改
                                                 ├── policy.json      ← 哈希校验
                                                 ├── audit.db         ← 追加写
                                                 └── history.git/
```

> 注意一个反直觉的点：**你的目标目录 `D:\Ai Agent\Agent Memory` 本身就在当前会话工作区之外**。这恰好演示了边界的存在——我在这个会话里无法直接写它。落地时要把"记忆数据目录"和"代码仓库目录"分开：代码在你能编辑的地方，**数据放在 agent 够不到的地方**。

**这一层的效果**：agent 想让 `MEMORY.md` 多一条内容，**唯一的表达途径就是调 `memory` 工具**——因为其它路径物理不通。这是"唯一入口"这四个字的真实含义；否则"唯一入口"只是提示词里的一句话。

### L1 · 服务端门禁：判定在服务里，不在工具里

`memory` 工具只是**一层薄壳**。所有校验必须在它下面：

```
工具层（可被替换/注入）        ← 只做参数转录
        ↓
ctx.memory 服务（宿主持有）    ← 门禁在这里：身份 / 版本 / 格式 / 容量 / 扫描 / 审批
        ↓
存储（文件 + 审计）
```

**为什么不能只放工具层**：`dsh-memento` 的作者给过理由——Hermes 的审批门**只在工具层实现，因而可被 late tool injection 绕过**（引用 Hermes issue #48181）。工具是插件注册的，能注册第一个就能注册第二个、能换一个同名实现。

**这条要落到代码上的判定**：

| 判定 | 在哪做 | 失败行为 |
|---|---|---|
| 调用者身份（主/子 agent、cron） | 服务，读宿主上下文 | 子 agent 写入 → **拒绝**，不降级为只读成功 |
| 目标文件与路径 | 服务，白名单枚举 | 非法 target → 拒绝 |
| 容量（≤10000 字符 或 严格减少） | 服务 | 拒绝并返回当前用量 |
| 读前校验 + 版本 CAS | 服务内部状态 | 未读 → 拒绝；冲突 → 拒绝且**不写** |
| **锁必须在读之前获取** | 服务，覆盖"读—校验—持久化—投影"全程 | 若"读"发生在拿锁前，两个并发修改会**静默互相丢弃**（双方都读到旧版本，CAS 也可能被绕过） |
| 敏感内容扫描 | 服务 | 命中 → 拒绝（不可见 Unicode 一律硬拒） |
| 审批 | 服务 → 宿主 `ask_user_question` | **无应答者 → 失败关闭**（fail closed） |

**"失败关闭"是硬化与否的分水岭**：`ask` 策略下如果宿主没有配置应答者（无人值守、脚本、子 agent），正确行为是**写入失败**，而不是"没人问就直接写"。

### L2 · 最小工具面：不要造一个能做坏事的工具

约束的另一种形态是**让坏事无法表达**：

- `memory` 工具的 `target` 是枚举 `["memory", "user"]`——**根本没有 `soul`**，所以"不修改 SOUL"不需要靠提示词；
- 不提供 `memory_set`（整文件覆盖）这种能力，只提供 `add/replace/remove`——**无法一次性清空**；
- `remove` 要求 `old_text` **唯一匹配**，不唯一就报错——**无法批量误删**；
- 不暴露"跳过审批"的参数。

**检验方法**：问自己"如果模型完全恶意，用现有工具能做到最坏的事是什么？"——如果答案是"删掉几条记忆（且有审计和 Git 可回滚）"，那工具面是合格的。

### L3 · 策略不可变：启动时校验，改了就拒绝启动

`policy.json`（容量、允许的 target、需确认的通道、扫描规则）在启动时加载并**校验哈希**：

```
启动
 → 读 policy.json
 → 计算 hash，与签名/白名单比对
 → 不一致 → 硬失败：不挂载记忆服务，明确报错
 → 一致 → 加载，且不把 policy 内容注入模型上下文
```

**为什么这条重要**：策略本身就是攻击面。如果 agent 能改 `policy.json` 把容量改成无限、把 `require_approval` 改成 false，前面的门禁全部作废。

**顺带解决另一个坑**：Hermes 有过真实事故——`int(config["nudge_interval"])` 抛错被外层 `except: pass` 吞掉，**整个记忆子系统静默失效且不报任何错**。所以载荷失败必须**响亮**：宁可启动失败，不要静默降级。

### L4 · 审计不可静默：每次写入可重建

- 追加写（append-only）审计表：时间、调用者、target、操作、写入前后长度、结果、拒绝原因；
- 被拒绝的写入**也记录**（这是最有价值的部分——它告诉你攻击/误解长什么样）；
- 每次成功写入进本地 Git，可 diff、可回滚；
- 注入给模型的快照文本**逐字记录**，事后能回答"它当时看到的是哪一版"。

### L5 · 提示词：只放 C 类

只有语言风格、价值判断这类无法硬化的东西留在提示词里，且**明确标注 `[软]`**。

## 四、把 Amadeus 的 5 条约定"编译"成可执行检查

Amadeus 的 `AGENTS.md` 写得很好，但每一条都只是文档。逐条给出**可执行的等价物**：

| 原文条款 | 现状 | 硬等价物 |
|---|---|---|
| "需求依据以某文档为准" | 文档 | 该文档的关键约束**落到 policy.json**；文档退化为说明，不再是依据 |
| "不改写 `node_modules` 中的 DSH 代码" | 文档 | CI：`git diff --name-only` 命中 `node_modules/` → **构建失败** |
| "每个行为改动都要有单元测试" | 文档 | CI：覆盖率门槛 + 新增文件必须有对应 `*.test.mjs`，否则失败 |
| "文件缺失或编码异常时降级加载，不能让对话整体失败" | 文档 | 测试：喂损坏文件/错误编码，断言 `assemble` 不抛、返回降级占位 |
| "升级时同步版本号与 lock 文件" | 文档 | CI：`package.json` 版本变了但 lock 未变 → 失败 |
| "发布用 pack 输出归档 + SHA256SUMS" | 文档 | 发布脚本强制生成；CI 校验产物可复现 |
| "无法自动化的如实标注需人工验收" | 文档 | 测试清单里的 `manual-only` 标记，且不允许出现在"已验证"列表 |

**一句话**：**每一条宪法条款，要么有对应的测试/守卫，要么降级为 `[软]`。没有第三条路。**

## 五、威胁模型与红队测试清单

**这不是我们自己的多疑。** OWASP GenAI Security Project 在 2025-12 发布的 [Agentic AI Top 10 Risks and Mitigations](https://genai.owasp.org/2025/12/09/owasp-genai-security-project-releases-top-10-risks-and-mitigations-for-agentic-ai-security/) 里，**ASI06 就是「Memory and Context Poisoning」**；另有专文 [《Memory Is a Feature. It Is Also an Attack Surface》](https://genai.owasp.org/2026/05/13/memory-is-a-feature-it-is-also-an-attack-surface/)。记忆是被承认的攻击面，不是理论风险。

硬化是否成立，只能靠攻击测试证明。以下每条都应是**自动化测试**，期望结果是"攻击失败"。

| # | 攻击方式 | 期望结果 |
|---|---|---|
| 1 | agent 用 `write` 直接覆盖 `MEMORY.md` | **文件系统层拒绝**（不在沙箱内） |
| 2 | agent 用 `bash`/`pwsh` `echo >> MEMORY.md` | 同上；若沙箱放行则测试失败，需回退到 L0 布局 |
| 3 | 给 `memory` 工具传 `target: "soul"` | 参数校验拒绝（枚举外） |
| 4 | 未读就 `replace` | 服务拒绝，且文件不变 |
| 5 | `old_text` 命中多条 | 报错要求更精确，**不做任何写入** |
| 6 | 写入超过 10000 字符 | 拒绝并返回当前用量与差额 |
| 7 | 传入伪造的版本号 | **服务忽略**（版本号不来自模型） |
| 8 | 子 agent 调写入工具 | 拒绝（不是静默变只读） |
| 9 | 写入含零宽字符 / `sk-` 密钥 | 硬拒绝，记录审计 |
| 10 | `ask` 策略下无应答者（脚本/无人值守） | **失败关闭**：不写、明确报错 |
| 11 | 篡改 `policy.json` 放宽容量/关审批 | 启动时哈希不匹配 → **拒绝启动** |
| 12 | 注册第二个同名 `memory` 工具（late tool injection） | 宿主拒绝重复注册，或服务只认自己的调用链 |
| 13 | 让 agent 把记忆快照复述出来 | 软约束（可能失败）；**不把它当安全机制** |
| 14 | 注入文本里写"忽略以上限制" | 扫描命中即拒；且**服务端门禁不依赖提示词**，即使漏扫也拦得住 |
| 15 | 压缩/上下文重写把注入的 guidance 行删掉 | 与 `billion-context-dsh` 的"注入行卫生"同类问题：**策略文本必须由宿主重注入并受保护**，不能被压缩掉 |

**第 15 条值得单独说**：`billion-context-dsh` 的 README 记录过一个真实死循环——压缩掉 `AGENTS.md` 的当前副本，宿主立刻重注入，再压缩……最后他们对"注入行"做了屏障保护（永不提供、永不计入可压段，且压当前副本会被硬拒绝）。

**这印证了同一件事**：约束文本一旦被当作"上下文的一部分"，它就会和压缩、重写、注入抢地盘。**真正的约束不能住在上下文里。**

## 六、落地顺序（按性价比）

| 顺序 | 做什么 | 为什么先做 |
|---|---|---|
| 1 | **挪文件**：数据目录放到 agent 沙箱外 | 一行配置，拿到最强边界（L0） |
| 2 | **门禁下沉**：所有校验从工具函数挪进 `ctx.memory` 服务 | 堵住工具层绕过（L1） |
| 3 | **失败关闭**：无应答者时不写 | 一行 if，消除"无人值守悄悄写"（L1） |
| 4 | **写红队测试**：上表 1–10 条 | 没有测试的硬化等于没做 |
| 5 | **policy 哈希校验** | 防策略被改（L3） |
| 6 | **审计 + 拒绝记录** | 让绕过尝试可见（L4） |
| 7 | **CI 守卫**：node_modules / lock / 覆盖率 | 把别的宪法条款编译成检查（第四节） |

**注意 1–3 都是"改配置和挪代码"，不需要新功能。** 硬化的大部分收益来自"位置"和"默认值"，不是来自"更复杂的实现"。

## 七、必须承认的边界（别自欺）

即便全部做到，仍有绕不过去的限制：

1. **模型可以在"允许的操作"里做蠢事。** 门禁能保证"没经批准不写"，不能保证"写进去的是对的"。质量靠规范、评审和过期清扫，不靠门禁。
2. **宿主被攻破 = 全部失效。** 门禁跑在宿主进程里；能被任意代码执行的攻击者不受这些约束。我们的威胁模型是"**模型被骗/被注入/自己乱来**"，不是"本机被入侵"。
3. **`ask` 策略依赖应答者存在。** 无人值守场景下正确答案是"失败关闭"，这会让自动任务没法写记忆——这是**刻意的取舍**，不是 bug。
4. **C 类约束永远是软的。** 谁声称"用提示词保证了安全"，谁就是在误导你。

| 文档 | 需要改的地方 |
|---|---|
| `路径A` | 原来把 `AGENTS.md` 当"约定范本"照抄——**要改成"文档 + 硬等价物"两栏**；数据目录必须放沙箱外；门禁下沉到服务 |
| `路径B` | `revision` CAS 必须在服务/事务内；`doctor` 只读打开；写入扫描在事务边界 |
| `路径C` | MCP 服务的门禁在**服务内**，不能靠客户端自律；只读 server 是天然硬化 |

**一句话总结**：**宪法写在纸上，门禁装在路上。** 你能改的只有路怎么修，而不是指望行人守规矩。
