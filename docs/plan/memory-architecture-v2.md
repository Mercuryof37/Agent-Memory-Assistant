# 记忆系统架构 v2 · 技术选型方案

> 状态：**P0–P4 已实现**（2026-10-17，见 [ADR-0013](../adr/0013-memory-v2-p0-p2.md) 与 [ADR-0014](../adr/0014-memory-v2-p3-p4.md)）。目标：在现有能力上重排一套**更清晰、用户可读性更强**的架构；不改掉已经跑通的底层，只把边界、入口和呈现理顺。

## 0. 结论先行

- **三层边界**：人设层（SOUL / USER / RULES，人维护、封存、注入）→ 事实层（不可变记忆记录 + 衍生目录，工具写入、卡片审批）→ 历史层（复用 DSH 原生会话检索 + 技能）。
- **不引入外部记忆服务**（Mem0 / Zep / Letta 等）：只借鉴它们的条目化、写入确认、时序与索引思路，不背外部依赖。
- **交互三条腿**：注入（常驻、分段预算）+ 审批卡片（已有）+ `/mem` 命令面（已有），三者后面共用同一套动作。
- **可读性目标**：一份文件一件事、一个动作一个入口、每次写入都有出处/审批/审计；用户看文件就知道系统在记什么。

## 1. 重读 Amadeus 后的六条设计约束

1. 记忆分层：SOUL 散文人格 / USER 条目偏好 / MEMORY 事实 / skills 方法 / session 历史。
2. 读有两条路：常驻注入（每轮可见）+ 工具按需查询；写有三条路：人手改、自动保存、agent 调工具。
3. 记忆工具语义：`target`（memory/user）、`query` 字面匹配、`all` 全文、`add/replace/remove`、**先读再写**、服务端版本冲突、唯一入口。
4. 会话查询：五个只读工具（search / event search / event read / event trace / session trace），底层可重建索引，权威仍是原始日志。
5. 提示词由 preset 组装，`MEMORY_GUIDANCE.md` 按开关与权限**分段路由**（confirm / direct / readonly / 子 agent 只读）。
6. 默认"用户全程参与"：每次修改前确认；比全自动更可控，代价是慢一点。

## 2. 我们现状盘点

| 层 | 已具备 | 半成品 | 缺口 |
|---|---|---|---|
| 人设层 | 封存哈希（soul/user/rules）、注入预算、规则解析 + 机器门禁 | — | **三个文件根本不存在**；无脚手架；无 guidance；无路由开关 |
| 事实层 | 不可变记录、出处（provenance）、supersede 时序、journal 审计、锁、重建、导出/清除、BM25 召回、提案 + 卡片 | `MEMORY.md` 只是事实目录；无"用户条目"概念 | USER 条目工具；与"人设文件"的边界约定 |
| 历史层 | DSH 原生 `sessionQuery`（FTS5 全文、事件读、谱系/替换追踪） | 尚未包装成模型工具 | `session_search` 等 5 个工具 |
| 方法层 | 原生 skills（`skill` / `skill_manager` 已就绪） | — | 与记忆的边界说明（不重复造） |
| 交互面 | `/mem` 命令面、审批卡片、CLI | 卡片只覆盖提案；USER/RULES 编辑无入口 | 统一确认流；README/手册的架构章节 |

## 3. 外部产品调研（2026-10，量级为公开检索，未能逐一实时校验）

> 说明：本机对外抓取被网络策略阻断（github/api 域名解析到非公网地址），下表的 stars 为检索到的**量级**，不是精确数；需要精确数时可补一次联网核对。

| 项目                          | 形态                      | 编辑模型                        | 读取                | 部署           | 社区量级   | 可借鉴                               | 为什么不整体采用                  |
| --------------------------- | ----------------------- | --------------------------- | ----------------- | ------------ | ------ | --------------------------------- | ------------------------- |
| **Mem0**（mem0ai/mem0）       | 记忆层库/服务                 | LLM 抽取 + 去重/更新              | 向量检索              | 云或自托管        | 4–5 万级 | 抽取/去重流水线、记忆操作语义                   | 外部服务 + 向量库，我们的量级不需要；抽取不可控 |
| **Zep / Graphiti**          | 时序知识图谱                  | 自动构建实体关系                    | 图 + 向量            | 云或自托管（Neo4j） | 1 万级   | 双时态（valid_from/valid_to）——我们已有    | 引入图数据库，运维重                |

| **Cognee**                  | 记忆/知识管线                 | pipeline 构建                 | 图 + 向量            | 自托管          | 6 千级   | 管线分层                              | 依赖重，场景偏 RAG               |

| **Basic Memory**            | Markdown + SQLite + MCP | 人/agent 编辑 md               | 索引检索              | 本地           | 2 千级   | **markdown 优先、索引可重建**（与我们的记录文件最像） | 没有审批/出处/时序，需我们自己补         |
| **MemOS**                   | 记忆操作系统（论文向）             | 多类型记忆调度                     | 多后端               | 自托管          | 3 千级   | 记忆分类学                             | 研究原型，工程化不足                |
| **Claude Code auto memory** | 产品内置                    | agent 写 MEMORY.md 索引 + 主题文件 | 每会话加载前 200 行/25KB | 内置           | —      | **MEMORY.md 只做索引**、容量信号           | 闭源能力，无法复用其实现              |
| **OpenClaw**                | 产品内置                    | USER/MEMORY + 每日笔记          | 注入                | 内置           | —      | § 分隔条目、独立小预算、截断注入副本               | 同左                        |
| **Hermes**（文章参考）            | 产品内置                    | 结束会话时整理                     | 注入                | 内置           | —      | "会话边界=记忆兑现点"                      | 自动化程度高、可控性低               |

**结论**：外部项目没有一款同时满足"本地优先 + 人可读 + 审批 + 出处 + 时序"；而这几样我们已经有了。因此选型是**借鉴分类学，复用原生能力，不引入依赖**。

## 4. 目标架构 v2

### 4.1 分层与边界

```text
┌──────────────── 人设层（人维护，封存，注入） ────────────────┐
│ SOUL.md   人格散文（≤200 字注入摘要）                        │
│ USER.md   条目式偏好（§ 分隔，≤1100 字注入，单文件≤10000 字） │
│ RULES.md  编号规则（[硬] 必须有检查才能生效，≤1200 字）        │
└───────────────────────────┬─────────────────────────────────┘
                            │ 会话开始注入（分段、按权限路由）
┌──────────────── 事实层（agent 写，必经审批） ────────────────┐
│ memories/{fact,pitfall,exp}/<id>.md   不可变记录 + 出处       │
│ MEMORY.md                             衍生目录（一行一条）    │
│ proposals/pending/ + journal          提案与审计              │
└───────────────────────────┬─────────────────────────────────┘
                            │ 工具/命令/卡片
┌──────────────── 历史层（只读，复用原生） ────────────────────┐
│ DSH sessionQuery：会话列表 / 全文检索 / 事件读 / 谱系追踪     │
│ skills：原生技能（方法沉淀，不由记忆插件重复实现）            │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 目录布局（对用户可见的部分）

```text
<记忆库>/
├── SOUL.md        人格（人写）
├── USER.md        偏好条目（人写；P1 起允许 agent 提议修改）
├── RULES.md       规则（人写；硬规则需检查）
├── MEMORY.md      事实目录（系统生成，勿手改）
├── memories/      每条事实一个文件
└── proposals/     待审提案
```

### 4.3 写路径矩阵（谁写、怎么批、怎么审计）

| 内容 | 写入口 | 审批 | 审计 |
|---|---|---|---|
| SOUL / RULES | 人编辑 + 重新封存（`/mem seal --accept`） | 人即审批 | 封存哈希 + journal |
| USER 条目 | 人编辑；P1 起 agent 走 `user_profile` 工具 | **每次修改卡片确认**（可配置） | 卡片选择 + journal |
| 事实记录 | `memory_record`（新）/ `memory_propose`（改） | 新记录免审（有出处约束）；修改必审 | journal + 记录 provenance |
| 删除 / 清除 | `memory_propose`（删除）/ `purge`（人，`--accept`） | 人决定 | journal 墓碑 |
| 会话历史 | 只读 | — | 原始日志 |
| 技能 | 原生 `skill_manager` | 按 DSH 原生策略 | 原生 |

### 4.4 模型工具面（现有 7 个 + 新增 6 个）

| 工具 | 状态 | 作用 |
|---|---|---|
| `memory_recall` / `memory_read` / `memory_context` | 已有 | 检索与上下文 |
| `memory_record` / `memory_propose` | 已有 | 写事实 / 提修订 |
| `memory_review` / `rules_list` | 已有 | 弹卡 / 读规则 |
| `user_profile` | **P1 新增** | 读/增/改/删 USER 条目：`query` 字面匹配、`all` 全文、`add/replace/remove`、先读后写、单条完整、§ 格式、10000 字上限 |
| `session_search` | **P2 新增** | 跨会话检索（原生 FTS5） |
| `session_event_search` | **P2 新增** | 单会话内检索 |
| `session_event_read` | **P2 新增** | 按 seq 读原文（±N 条窗口） |
| `session_event_trace` | **P2 新增** | 事件的替换链与引用关系 |
| `session_trace` | **P2 新增** | 会话谱系（祖先/后代） |

约束：`user_profile` 与记忆写入一样受 `delegationDepth` 限制（子 agent 只读）；会话工具全只读。

### 4.5 注入面（preset 分段）

|    顺序 | 段               | 来源                                    | 预算     |
| ----: | --------------- | ------------------------------------- | ------ |
| -1000 | DSH 固定开场        | 原生                                    | —      |
|   100 | SOUL            | `SOUL.md`（空则不注入）                      | 200 字  |
|   110 | MEMORY_GUIDANCE | 按开关/权限选段（confirm / direct / readonly） | 300 字（P3） |
|     — | DSH 一等公民说明      | 原生                                    | —      |
|   150 | RULES           | `RULES.md`（超预算硬失败）                   | 1200 字 |
|   200 | USER            | `USER.md`                             | 1100 字 |
|   300 | MEMORY          | 事实目录（派生）                              | 1200 字 |
|     — | 总计              |                                       | 3700 字（guidance 落地后 4000） |

要点：SOUL 只注入摘要、USER 注入全文（条目短）、RULES 全文（超预算硬失败）、目录只列活动项、空文件不产生空标题。

### 4.6 交互面（同一动作，三种入口）

- **卡片**：记忆修订（已有）→ USER 条目修改（P1）→ 任何需要人拍板的写入；
- **`/mem`**：`proposals` / `decide` / `read` / `recall` / `inspect` / `seal` / `export` …（已有）；
- **CLI**：脚本、修复、批量场景（已有）。
- 三者调用同一实现，文案与结果一致。

### 4.7 可读性设计

- **文件即视图**：`MEMORY.md` 一行一条、`USER.md` 一条一段、错误信息点名文件与键；
- **格式契约**：USER 用单独一行 `§` 分隔，单条非空完整、不内嵌 `§`；单文件上限 10000 字；
- **命名一致**：模型工具 `memory_*`、会话工具 `session_*`、人命令 `/mem`；
- **文档分层**：使用手册（人话）+ 本架构文档（决策）+ ADR（历史原因）。

## 5. 关键决策（含被否方案）

| # | 决策 | 理由 | 被否方案 |
|---|---|---|---|
| D1 | 事实层继续用不可变记录，`MEMORY.md` 只做目录 | 出处、审批、时序、审计都建立在记录上；直改 MEMORY.md 会绕过全部 | 学 Amadeus 直接编辑 MEMORY.md 条目 |
| D2 | USER 用条目文件，不用记录库 | 条目短、整体注入、人可读可手改 | 把偏好也做成带出处的记录（会膨胀、注入难控） |
| D3 | 会话检索复用原生 `sessionQuery` + FTS5 | 零新依赖，索引可重建，权威是原始日志 | 自建 SQLite 索引（重复劳动） |
| D4 | 默认"确认后写入"，direct/readonly 做开关 | 与文章默认一致；弱模型场景更稳 | 默认全自动 |
| D5 | 不加向量检索 | 记忆量级 < 1k，BM25 + 字面足够 | 引入向量库（成本/依赖大于收益） |
| D6 | 不引入外部记忆服务 | 本地优先、隐私、可控 | Mem0/Zep/Supermemory 托管 |

## 6. 分阶段路线

| 阶段 | 内容 | 验收 | 估时 |
|---|---|---|---|
| **P0 人设层落地** | `mem scaffold`（或 `init --human`）生成 SOUL/USER/RULES 模板并封存；`doctor`/`inspect` 提示缺失；注入拆成 SOUL/GUIDANCE/USER/MEMORY 四段；手册补"人设文件"章节 | 模板幂等；启动后注入出现四段；改文件未重封 → 启动失败并点名 | 1 d |
| **P1 USER 条目** | `user_profile` 工具（读/增/改/删、先读后写、§ 格式、10000 上限、服务端冲突）+ 卡片确认；USER 默认不封存（可配） | 单测覆盖格式/冲突/上限；桌面弹卡确认后文件更新；注入立即生效 | 1.5 d |
| **P2 会话五工具** | 包装原生 `sessionQuery`：`session_search`、`session_event_search`、`session_event_read`、`session_event_trace`、`session_trace`；只读、结果截断与来源标注 | 真实会话里跨会话检索到历史原话；trace 返回替换链 | 1 d |
| **P3 guidance 路由** | `MEMORY_GUIDANCE` 分段（confirm/direct/readonly/子 agent 只读）；配置 `[personalization]` 三键；preset 分段 | 三种模式下模型行为与提示词一致；子 agent 只有读工具 | 1 d |
| **P4 打磨** | eval 扩展到 USER 场景；手册/架构/ADR 收口；DSH 升级兼容检查 | 文档齐、eval 基线更新、`ci` 全绿 | 1 d |

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 封存摩擦：改 SOUL/USER/RULES 要重封 | 卡片/命令提供一键重封；USER 默认不封存（可配） |
| 配置膨胀（现 22 键 + 3 开关） | 收进 `[personalization]` 段，三件套（schema/模板/docs）一次改齐 |
| 双写路径（USER 文件 vs 记录） | 边界写进 guidance 与手册：偏好→USER、事实→记录；代码层不允许错写 |
| 工具数量上升（7→13） | 分阶段注册；guidance 说明"什么时候用哪个"；子 agent 只读 |
| DSH 破坏式更新 | 只依赖四类稳定面：`tools`、`commands`、`userQuestions`、`sessionQuery`；版本锁定 + compat 记录 |

## 8. 需要你拍板的三件事

1. **USER.md 允许 agent 写吗？** 推荐：允许，但每次修改走卡片确认（默认）；可切到"人专属"。
2. **会话工具先做几个？** 推荐：五个一起（原生已全部具备，trace 对排查很有用）。
3. **USER.md 默认封存吗？** 推荐：不封存（否则 agent 写完还要人手动重封）；SOUL/RULES 保持封存。

---

附：本方案与 Amadeus 的对应关系——SOUL/USER/RULES = 人设层；MEMORY 目录 + 记录 = 事实层；`memory` 工具语义 = 我们的 `memory_*` + `user_profile`；五个 session 工具 = 原生 `sessionQuery` 的包装；`MEMORY_GUIDANCE` 分段 = preset 分段 + `[personalization]` 开关；"确认后写入" = 已有的卡片审批。
